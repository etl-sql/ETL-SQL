- [ ] **DATASET — Cross-Report Shared Data Sets** *(Report Portal feature — enables persistent, encrypted, reusable data sets shared across reports)* — Datasets are materialized query results persisted to disk as encrypted Parquet files, registered in `portal.db`, and reusable by any report with permission via `USE DATASET`. They are server-bound (machine-key encrypted, not portable), default to private, and refresh on a schedule or on-demand from the Portal. The foundation (CREATE DATASET, DROP DATASET, manifest metadata, auto-refresh scheduling, linting infrastructure, lineage tracking) is already fully implemented. All new phases build on that foundation.

    **Current State (already implemented):**
    - `CREATE DATASET #name [REFRESH EVERY <n>s|m|h|d] [TTL <n>s|m|h|d] [COMPRESS] [ENCRYPT = MACHINE|PASSWORD|KEYFILE] AS <source_query>` — fully parsed, validated, and materialized to in-memory temp table
    - `DROP DATASET #name` — removes from active definitions
    - `DatasetManifest` persisted in snapshot.json with TempTableName, RefreshInterval, Ttl, LastRefresh, RowCount
    - Auto-refresh scheduling in `DashboardService` (shortest interval across all datasets in report)
    - Two lint rules: encryption credentials completeness, refresh interval format
    - Lineage tracking: dataset operations recorded with source table links, Mermaid cylinder shape rendering
    - Language service suggests DATASET keyword in CREATE completions

    - **Phase 1 — Portal.db Registry & Schema** *(prerequisite for all other phases)*: Add `datasets` table to `portal.db` with columns: `Id`, `Name`, `FolderPath` (namespace), `ParquetFilePath` (absolute path on server), `OwningReportId` (nullable — report that last created/refreshed it), `SourceQuery` (stored from `CreateDatasetStatement` for Portal-triggered refresh), `AccessLevel` (Public/Private), `LastRefresh` (UTC), `Ttl`, `RefreshInterval`, `RowCount`, `ColumnSchema` (JSON — column names and types for Portal grid), `CreatedAt`, `UpdatedAt`. Add portal permissions rows for dataset objects (viewer, editor, owner roles). Add EF Core migration. Add `DatasetRegistryService` in ReportPlayer with methods: `RegisterOrUpdate`, `Lookup(name, folderPath)`, `Exists(name, folderPath)`, `SetStale`, `ListAll(callerPermissions)`, `Delete`. `CreateDatasetStatementHandler` calls `RegisterOrUpdate` after successful materialization.

    - **Phase 2 — Parquet Persistence via Macro Expansion + Machine-Key Encryption** *(enables cross-session and cross-report data sharing — reuses existing connector and job infrastructure entirely)*: `CreateDatasetStatementHandler` becomes a macro expander. It resolves the machine-local output path (e.g. `data/datasets/<name>_<id>.parquet`) then synthesizes and dispatches AST nodes through the existing handler table — no new serialization code: (1) `CreateConnectionStatement` for a PARQUET connection at the resolved path with `COMPRESSION=SNAPPY` and `ENCRYPT=MACHINE` options; (2) `InsertStatement` (`INSERT INTO <conn>.FILE SELECT ...` using the source query from `CreateDatasetStatement`); (3) `CreateJobStatement` at the REFRESH EVERY interval whose script body is the same two statements above. The `CreateConnectionStatementHandler`, `InsertStatementHandler` (`PerformBatchTransfer` → `ParquetDataSource.WriteBatches()`), and `CreateJobStatementHandler` are called unchanged. Write the generated ETL-SQL script to a sidecar `.etlsql` file (e.g. `data/datasets/<name>.etlsql`) alongside the Parquet file — same text stored in the `JobDefinition.Script` field — for troubleshooting and manual re-execution. **One new addition required:** add `ENCRYPT=MACHINE` to `EncryptionOptions.cs` as a recognized value using Windows DPAPI (`ProtectedData.Protect`) on Windows and OS keyring equivalent on Linux; the rest of the encryption pipeline in `ParquetDataSource` is already wired. Add a **staleness check at CREATE time**: if the dataset exists in portal.db and `LastRefresh + TTL > UtcNow`, skip macro expansion entirely and load rows from the existing Parquet file into the temp table using `CreateConnectionStatement` + `SELECT * FROM <conn>.FILE`. Add a lint rule: reject `ENCRYPT = PASSWORD` and `ENCRYPT = KEYFILE` on `CREATE DATASET` — machine-key is the only valid mode for persisted datasets; PASSWORD and KEYFILE remain valid for other report encryption uses.

    - **Phase 3 — USE DATASET, SHOW DATASETS, REFRESH DATASET Statements** *(unlocks cross-report consumption)*:
      - **`USE DATASET &name`** — new token (`USE`+`DATASET`), new `UseDatasetStatement` AST record (Name, FolderQualifiedName), new `UseDatasetStatementHandler`. Handler: looks up dataset in portal.db via `DatasetRegistryService.Lookup()`. Checks caller's portal permissions — if dataset is PRIVATE and calling report is not the owner, throw `ExecutionException` with message "Dataset '&name' is private and cannot be used by this report." If caller has permission: decrypt and deserialize the Parquet file into a `#name` temp table in the current execution context. Emit a **runtime warning** (not a lint error) if `UtcNow - LastRefresh > TTL`: "Dataset '&name' data is X days old. Results may not reflect current data." If dataset not found in portal.db, throw `ExecutionException` with "Dataset '&name' not found. Verify the name and folder path, or check that the owning report has been executed at least once."
      - **`SHOW DATASETS`** — new `ShowDatasetsStatement` AST record, handler queries `DatasetRegistryService.ListAll(callerPermissions)` and returns a result set with columns: Name, FolderPath, AccessLevel, RowCount, LastRefresh, IsStale, RefreshInterval, Ttl. Only PUBLIC datasets and PRIVATE datasets owned by the calling context are returned.
      - **`REFRESH DATASET &name`** — new `RefreshDatasetStatement` AST record, handler re-executes the stored SourceQuery from portal.db (re-materializes and re-writes Parquet), updates LastRefresh in registry. Requires editor/owner permission.
      - **Implied USE in same report**: No USE statement is needed when the same report file creates the dataset — the dataset is already in the execution context as a temp table. The USE statement is only required when consuming a dataset from a different report. Add a lint hint (informational, not warning): "USE DATASET is not required here — '&name' was created earlier in this script."

    - **Phase 4 — ACCESS PUBLIC|PRIVATE Syntax & Lint Rules** *(access control at authoring time)*:
      - Extend `CREATE DATASET` grammar with optional `ACCESS PUBLIC` or `ACCESS PRIVATE` clause (default: PRIVATE when omitted). Update `CreateDatasetStatement` AST record to add `AccessLevel` property. Update `CreateDatasetStatementHandler` to persist AccessLevel to portal.db. Update Grammar.md, DATASET.md help file, and Report_SQL_Guide.md.
      - **Lint rule — unknown access level**: Error if ACCESS value is not PUBLIC or PRIVATE.
      - **Lint rule — USE before CREATE in same file**: Warn if `USE DATASET &X` appears before `CREATE DATASET #X` in the same script file. Ordering constraint: CREATE must precede USE within the same execution.
      - **Lint rule — PRIVATE demotion with consumers**: When ACCESS changes from PUBLIC to PRIVATE on an existing dataset (detected by comparing new script's ACCESS level against portal.db registry), warn: "Dataset '&name' is currently PUBLIC and has N reports using it via USE DATASET. Changing to PRIVATE will prevent those reports from running." Requires portal.db query at lint time via `DatasetRegistryService` (lint-time portal.db access is acceptable here because it is a project-local file, not a remote service).
      - **Runtime error — PRIVATE access violation**: When `UseDatasetStatementHandler` detects the dataset is PRIVATE and the calling report is not the owner, throw a clear `ExecutionException`. In Portal context, surface this as a user-facing error modal: "This report requires access to dataset '&name' which is set to private. Contact the report owner to request access or change the dataset to PUBLIC."

    - **Phase 5 — Portal Dataset Explorer** *(datasets as first-class Portal objects)*: Add `DatasetController` to `ETL-SQL.ReportPortal`. Datasets appear in the Portal navigation tree alongside Folders and Reports — represented by a cylinder/stack icon. Portal nav object click opens a detail view with two panels:
      - **Metadata panel**: Dataset name, folder path, owner report (linked), ACCESS level badge (Public/Private), RefreshInterval, TTL, last refreshed timestamp, IsStale badge (amber) showing "X days old" if stale, RowCount, encrypted/compressed status flags, and any TAGS defined on the dataset's source query columns.
      - **Data grid panel**: Paginated rows from the Parquet file (decrypted server-side, never exposed as raw file). Column header filters — same VS Code results panel behavior: click column header to filter by value, multi-value filter, clear filter. Requires portal viewer permission on the dataset. PRIVATE datasets are visible in the explorer only to the owning report's folder and to portal admins — they do not appear in other users' navigation trees.
      - **Refresh button**: Visible to users with editor/owner permission. Triggers `REFRESH DATASET` API endpoint. Shows spinner + last-refreshed timestamp update on completion. If refresh fails, shows error with partial stack trace.
      - **Permission management**: Owner can toggle PUBLIC/PRIVATE from the detail view. Changing to PRIVATE shows a confirmation modal if N consumer reports exist (mirrors the lint-rule warning). Owner can grant viewer/editor access to specific users or roles.
      - **API endpoints**: `GET /api/datasets` (list all visible to caller), `GET /api/datasets/{id}` (metadata), `GET /api/datasets/{id}/rows?page=&pageSize=&filters=` (paginated data), `POST /api/datasets/{id}/refresh` (trigger refresh), `PATCH /api/datasets/{id}` (update access level / metadata), `DELETE /api/datasets/{id}` (calls DROP DATASET logic + removes Parquet file).

    - **Phase 6 — Portal-Triggered Refresh** *(closes the loop on server-managed lifecycle)*: When `POST /api/datasets/{id}/refresh` is called, the Portal retrieves `SourceQuery` and connector context from portal.db, spins up an `EngineRunner` execution session, re-evaluates the source query against live data, writes updated Parquet file, and updates `LastRefresh` + `RowCount` in registry. Refresh runs on a background thread — Portal returns `202 Accepted` immediately with a `Location` header pointing to a status endpoint (`GET /api/datasets/{id}/refresh-status`). Concurrent refresh guard: if a refresh is already in-progress for the same dataset, return `409 Conflict` with message "Refresh already in progress." Use `AsyncReaderWriterLock` (same pattern as `SnapshotStore`) to guard Parquet file writes against concurrent reads from `UseDatasetStatementHandler`. On failure, portal.db refresh status is set to `Failed` with error message; the stale Parquet file is preserved so existing reports continue to function with old data. Emit an admin notification (Portal notification bell) on failure.

    - **Phase 7 — Language Service Enhancements** *(developer experience)*: `USE DATASET` completions in LSP — after `USE DATASET `, query portal.db registry and suggest known dataset names with folder paths. Hover on `&datasetName` in a USE DATASET statement shows dataset metadata from portal.db: last refresh, row count, access level, staleness. `SHOW DATASETS` keyword completions. Grammar.md, DATASET.md help file, and Report_SQL_Guide.md updated to cover USE DATASET, SHOW DATASETS, REFRESH DATASET, and ACCESS PUBLIC|PRIVATE syntax in full.

- [ ] **Fuzzy Matching — Full Feature Set** — See `Docs/Strategy/FuzzyMatching_Strategy.md` for the complete design. Five phases in recommended order:
    - **Phase 1 — `NORMALIZE()` function** *(go first — highest ROI, smallest scope)*: Domain-aware string preprocessing with presets for COMPANY, PERSON, ADDRESS, PHONE, EMAIL. Eliminates surface variation before any similarity algorithm runs.
    - **Phase 2 — String Similarity & Phonetic Functions**: `SIMILARITY(a, b, algorithm)` supporting JAROWINKLER, LEVENSHTEIN, TRIGRAM, JACCARD, TOKENSORT. Engine-level `SOUNDEX`, `METAPHONE`, `DMETAPHONE`. Foundation for all subsequent phases.
    - **Phase 3 — Blocking Utilities**: `NGRAMS(s, n)` and `NGRAM_TOKENS(s)` to support user-built inverted-index blocking patterns. Documented cookbook recipes for manual block → score → rank pipeline.
    - **Phase 4 — `FUZZY JOIN` syntax** *(biggest ergonomic win)*: `FROM #a FUZZY JOIN #b ON SIMILARITY(...) > 0.80 KEEP BEST 1`. Built-in trigram blocking index; `LEFT FUZZY JOIN` variant; `__score` injected into result. Semantics for threshold/cardinality/ties fully documented in strategy doc.
    - **Phase 5 — Embedding-Based Semantic Matching** *(defer until Phase 4 ships)*: `EMBED(col, endpoint, model)` via pluggable HTTP endpoint (Ollama/OpenAI-compatible). `VECTOR` column type. `SIMILARITY(a, b, 'COSINE')`. For the cases where string algorithms fail entirely (semantic variation).
