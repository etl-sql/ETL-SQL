## Finding 1 — Snapshots silently encrypt with a public constant key in standalone mode (Medium)

**Where:** `src/ETL-SQL.Reporting/SnapshotPackageService.cs:40` and `:284-302`
(`DefaultDevAtRestKey`, `DeriveAesKey`).

```csharp
private static readonly string DefaultDevAtRestKey =
    Convert.ToBase64String(Enumerable.Range(1, 32).Select(v => (byte)v).ToArray());
// ...
private static byte[] DeriveAesKey(string? base64Key, string configName)
{
    if (string.IsNullOrWhiteSpace(base64Key))
        base64Key = DefaultDevAtRestKey;   // <-- silent fallback to bytes {1,2,...,32}
    ...
}
```

`.etlsnap` snapshot packages (which hold report **result data**, potentially PII) are AES-GCM
encrypted. When `Portal:Dataset:AtRestKey` is unset, the key silently derives from a constant that
is committed to the source tree — i.e. effectively *no confidentiality*, while the file still looks
encrypted (magic header, GCM tag).

**Why it's only Medium, not High:** In a correctly configured **production** Portal this path is
unreachable. `DatasetAtRestKeyValidationService` runs at startup and calls `StopApplication()`
(fail-closed) when `AtRestKey` is missing and `AllowMachineFallback=false`
(`DatasetAtRestKeyValidator.Validate` → `Severity.Fatal`). So production must set a real key, which
the snapshot path then uses.

**The actual gap — standalone mode and the CLI:**
- With `AllowMachineFallback=true` (the documented dev/standalone mode), dataset caches fall back to
  host-bound `ENCRYPT=MACHINE`, but **snapshots fall back to the world-known constant** instead.
  Two at-rest stores, same config, divergent and undocumented strength — and the weaker one is silent.
- The CLI/local execution path (`dotnet run -- run script.etlsql`) has no startup validator, so any
  snapshot it writes uses the constant key by default (this is the intended dev convenience per the
  CHANGELOG, but it is invisible to the user).

**Resolution (implemented):** Option 1. When `AtRestKey` is unset, `SnapshotPackageService` now
protects the package with `MachineBoundCrypto` — the *same* host-bound `ENCRYPT=MACHINE` primitive
dataset caches use (DPAPI `LocalMachine` on Windows; authenticated AES-256-GCM keyed from the machine
id elsewhere). The source-public `DefaultDevAtRestKey` constant was removed. On read, packages are
auto-detected by the `ETLSNAP1` magic: keyed packages take the key-managed path (which now **fails
closed** via `DeriveAesKey` if the key is absent), and machine-bound packages route to
`MachineBoundCrypto.Unprotect`. A one-time warning is logged when the host-bound fallback is in
effect (silent in the CLI, which injects `NullLogger`). The `AtRestKey` config doc now states it
covers snapshots too. Tests:
`SaveAsync_WithNoAtRestKey_UsesHostBoundMachineEncryption_AndRoundTrips` and
`LoadAsync_KeyedPackage_FailsClosed_WhenKeyLaterRemoved`.

**Verified, not a bug:** I initially suspected a round-trip failure (`Encrypt` stamps version `"v1"`
when `AtRestKeyVersion` is blank, but `ResolveReadKey` compares against the blank config value).
`DatasetConfig.AtRestKeyVersion` **defaults to `"v1"`**, so the default-config round-trip matches.
Only an operator who explicitly blanks `AtRestKeyVersion` would hit a decrypt failure — low risk.

## Finding 2 — Unauthenticated AES-CBC in the non-Windows machine-key fallback (Low) — FIXED

**Where:** `src/ETL-SQL.Core/Common/CryptoUtils.cs` (`ProtectGeneric`/`UnprotectGeneric`).

The cross-platform `ENCRYPT=MACHINE` fallback (used where Windows DPAPI is unavailable) was raw
AES-CBC with a prepended random IV and **no MAC** — malleable (bit-flipping / padding-oracle classes
of attack). **Fixed:** the path is now encrypt-then-MAC. Two sub-keys are derived from the machine
key material via HKDF-SHA256 (distinct `info` labels for encryption vs MAC); the payload is
`MAGIC || IV || AES-CBC ciphertext || HMAC-SHA256(MAGIC||IV||ciphertext)`, verified with
`CryptographicOperations.FixedTimeEquals` before decryption. Pre-magic blobs are detected as legacy
CBC-only and still decrypted (read compatibility for already-persisted session/metadata state).
Tests: `MachineGenericEncryption_RoundTrips_AndDetectsTampering`,
`MachineGenericEncryption_ReadsLegacyCbcOnlyBlob`.

## Finding 3 — `machine.key` file permissions (Low / defense-in-depth) — FIXED

**Where:** `src/ETL-SQL.Core/Common/CryptoUtils.cs` (`GetMachineKey`).

The generated 32-byte machine key was written with `File.WriteAllBytes` (default umask). **Fixed:**
on Unix the key file is now created owner read/write only (`0600`) atomically via
`FileStreamOptions.UnixCreateMode` (so it is never briefly world-readable), and the `etl-sql`
directory is created `0700`. On Windows the per-user profile already scopes it, and `Protect` uses
DPAPI rather than this path, so the generic file path runs only on non-Windows.

## Finding 4 — Stale release-tooling references in CLAUDE.md (Info) — FIXED

CLAUDE.md's "Releasing" section pointed at `scripts/Invoke-Release.ps1` / `scripts/invoke-release.sh`
(which never existed) and described auto-push/tag/watch behavior the real tooling does not perform.
**Fixed:** the paragraph now describes the real flow — `Set-Version.ps1` → `Test-PreRelease.ps1`
(gate) → `Master-Release.ps1` (packaging via `publish_release.ps1`, emitting `release/`,
`sha256sums.txt`, `sbom.json`) → **manual** `git tag`/push — and `Docs/Release_Checklist.md` now

## Areas reviewed and found sound (no action)

- **Service-account token exchange** (`ServiceAccountTokenController.cs`): `[AllowAnonymous]` +
  `[EnableRateLimiting("auth")]`; secrets stored as `SecretHash` via `IPasswordHasher<ServiceAccount>`
  (PBKDF2); constant-time behavior via a `DummyHash` verify when the client is unknown/invalid;
  issued roles are the **intersection** of the account's roles and the owner's *current* roles, so a
  token can never exceed (or outlive a downgrade of) its owner's privileges; `CanAuthenticate` checks
  enabled/revoked/expiry/owner-active; action is audited.
- **New admin endpoints** (`AdminController.cs`): class-level `[Authorize(Roles = "Admin")]` covers
  the new `metrics/operational`, `metrics/usage`, and historical execution-load endpoints.
- **Config export** (`AdminController.cs:1273`): exports secret **placeholders**, not values, and
  audits the count; `GetOrchestratorSettings` returns `HasApiKey` (bool), never the key.
- **Snapshot AES-GCM** (`SnapshotPackageService.Encrypt/Decrypt`): per-message 96-bit random nonce,
  128-bit tag, key-version as AAD, key-rotation via `PreviousAtRestKeys`/`LegacyAtRestKeyVersion`.
- **Snapshot zip handling**: entry names sanitized on write (`SanitizeEntryName`); on read everything
  stays in `MemoryStream` and entries are fetched by name with `GetEntry` — nothing is extracted to
  the filesystem, so there is no zip-slip / path-traversal exposure.
- **`HASH()` SQL function** (`CryptoUtils.cs:751`): MD5/SHA1 options are user-selected data checksums,
  not a security primitive — acceptable.
- **Lateral column aliases** (this release, `SelectStatementHandler.cs`): bind-time inlining; a real
  source column always wins over a same-named alias; pushdown guarded so a lateral alias can't leak
  into remote SQL. Covered by `StmtLateralColumnAliasTests` and the full suite (3891 passing).
