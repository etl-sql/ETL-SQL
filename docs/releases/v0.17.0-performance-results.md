# v0.17.0 Performance Results — Scale Certification

**Status:** Decision record. **There is no v0.17.0 performance regression.** Both certification
tiers pass their baselines when measured correctly. The failures seen during the release gate were
produced by the measurement method, not by the code.

This also resolves the question left open by
[v0.15.0](v0.15.0-performance-results.md) and deferred again through v0.16.0.

## Outcome

| Tier | Result with warm-up | Result during the gate |
| :--- | :--- | :--- |
| Smoke | `[OK] No failing regressions` (2 warnings) | 4 failures, 7 warnings |
| Standard | `[OK] No failing regressions` (1 warning) | 7 failures, 3 warnings |

Correctness passed throughout: **13/13 scenarios**, every run, in every configuration.

## Root cause: cold measurement, not slow code

`Test-ScaleCertification.ps1` rebuilds the solution and then immediately measures. The first run
after a build measures JIT compilation and antivirus scanning of fresh binaries. Because the release
gate runs scale certification **last** — after roughly 70 minutes of test lanes, a Docker
integration lane, and container churn — those readings are the least trustworthy of the entire gate.

The size of the effect is larger than anything it was being used to detect:

| Measurement of the **identical commit** | ELAPSED_MS |
| :--- | ---: |
| `StreamingSelect_1000000`, cold, end of gate | 8977 |
| `StreamingSelect_1000000`, cold, standalone | 7673 – 7880 |
| `StreamingSelect_1000000`, warmed | 5013 – 5129 |

**A 56% spread on identical code.** Any comparison drawn against a threshold inside that range is
noise. `ExternalJoin_50000` behaves the same way: 878–888 ms cold, **607 ms warmed**, against a
552 ms baseline.

## Controlled comparison

Measured by checking both commits out into **one** worktree — so path, disk locality, and antivirus
history are identical for both arms — with a discarded warm-up run and interleaved repetitions:

| Build | Median | Runs |
| :--- | ---: | :--- |
| `v0.16.0` | 5017 ms | 6342, 5003, 5017 |
| `v0.17.0` (HEAD) | 5114 ms | 5114, 5076, 5126 |

**+1.9%** — within noise. v0.17.0 does not regress the engine.

### The error that produced the false alarm

An earlier comparison appeared to show v0.16.0 passing the standard baseline while v0.17.0 failed
it, and was reported as conclusive. It was not: **v0.16.0 was measured in a separate warm worktree
and v0.17.0 in the main repository immediately after a full gate run.** That is a comparison of two
locations in two thermal states, not of two commits. Repeating it in a single worktree removed the
entire effect.

The warning sign was present and was misread: identical retention-only code measured 6598 ms and
7673 ms on consecutive runs. That 16% spread was wider than the ~14% effect being investigated,
which should have stopped the investigation and redirected it at the instrument.

## Required measurement method

Any certification number used for a release decision must satisfy all of:

1. **Discard a warm-up run** after every build. Never measure the first run of fresh binaries.
2. **Compare within one working directory.** Check the other commit out into the same worktree
   rather than comparing across two checkouts.
3. **Interleave arms** (A, B, B, A, …) so drift during the window hits both equally.
4. **Report the within-arm spread next to the delta.** A delta smaller than the spread is not a
   result. With this method the noise floor is ~2%; without it, ~56%.
5. **Never decide from a single sample.** One sample read 717 ms where five read 888 ms on the same
   code.

Harnesses implementing this are described in the v0.18.0 TODO item; the intent is to fold them into
`Compare-CertBaseline.ps1` so the gate cannot produce this class of failure again.

## Consequences for the gate

- The scale phases do **not** need `-SkipScale`; both tiers pass when warmed.
- `baseline-smoke.json` (2026-07-05) and `baseline-standard.json` (2026-07-18) are **valid** and
  must not be re-blessed. An earlier bless was correctly reverted in `e3fa80af`; blessing cold
  readings would have baked a 56% measurement artifact into the reference permanently.
- Scale certification should run **before** the long test lanes, or the gate should quiesce the
  machine first. Running it last guarantees the worst measurement conditions of the whole gate.

## Residual observation, not a blocker

`StreamingSelect_1000000` GC_PAUSE_MS warns at +29% (56.1 → 72.5 ms) against a 20% warning band,
warmed and reproducible. Elapsed and throughput are in band. The data-quality work adds per-row
allocation, so a modest GC increase is plausible and worth confirming in v0.18.0 — as a warning to
investigate, not a release blocker.

Two changes made while investigating are retained on their own design merits:

- `565c4646` — rule-free `SELECT`s no longer retain every input row alongside its projection. The
  improvement figure quoted in that commit was measured before the methodology was corrected and
  should not be relied on; the change is correct regardless.
- `770e2425` — `INT(n,+)` sign constraints are parsed once per declared type instead of once per
  row. Documented at the time as having no measurable effect.
