# MI01 Services Own Their Configuration (v0.23.0 design note)

**Status:** Approved by the owner, 2026-11-21 (approach A; the §5 one-time slimming included). Covers TODO §2.7 (MI01) and slice 1 of the
[Windows Installer roadmap entry](../../ROADMAP.md#windows-installer--the-msi-copies-files-and-registers-services-only).

## Summary

- The MSI stops running scripts. `WriteJwt`, `ReadSettings`, `RestoreSettings`,
  `configure-portal-jwt.ps1`, `installer-actions.js` and the `PREVIOUS_SETTINGS` property go.
- `appsettings.json` becomes the operator's file: installed once, never overwritten by an upgrade.
  The release defaults move to a new MSI-owned `appsettings.defaults.json`, loaded underneath it.
- The old product is removed after the new one is installed (`RemoveExistingProducts` after
  `InstallExecute`), so a v0.22.0 `appsettings.json` is kept as it is. Nothing reads or copies
  settings during the upgrade.
- Installer choices (Portal surface and modules) and install facts (install folder, Orchestrator
  job database path) are written by the MSI as registry values, and every host reads them.
- On first start, the Orchestrator and Portal create the missing secrets, move any secret found in
  `appsettings.json` into `appsettings.secrets.json`, and create the first-run sign-in file.

## Why

From the roadmap entry: script custom actions run as LocalSystem inside the install, Microsoft
discourages them as fragile and antivirus-sensitive, and a failure inside them shows only in the
msiexec log. After MI01, a configuration failure is a service start failure with the reason in
the service log, and the MSI copies files and registers services.

## Goals

- No script custom actions. (`CloseApplication` is slice 2 and was already replaced by
  `ServiceControl`; this design adds no custom action of any kind.)
- Fresh install: both services start with generated secrets; the Portal has a one-time sign-in.
- Upgrade from v0.22.0 and from every later release: secrets, operator settings (including keys
  the release does not know, like the certification's `UpgradeSentinel`) and installer choices are
  kept; keys new in the release take their defaults.
- Secrets never land in, or stay in, the world-readable `appsettings.json`.

## Non-goals

- DEB and other packages. `build-linux-packages.sh` keeps its install-time configuration; the
  first-start code must be a no-op when the secrets already exist, so it is safe there later.
  Moving DEB to first-start generation is a follow-up, not MI01.
- Uninstall behavior. Uninstall still removes `appsettings.json` and keeps the secrets file and
  data, as today; `admin purge-data` removes the rest (MI04).
- Changing install paths, profiles, service names, ports or the WiX version (roadmap boundaries).

## Anti-goals

- Generating secrets in a developer or container run. A missing JWT secret outside an installed
  service must keep failing fast (see the Portal JWT secret rules); first-start generation runs
  only for an MSI-installed host.
- Two services generating different values for a secret they share (`Orchestrator:ApiKey`,
  `IdentitySigningSecret`).
- A partially written secrets file, or one readable by ordinary users at any moment.

## Constraints found in the code

- `RemoveExistingProducts` runs early today (`afterInstallValidate`), so the old product's
  `appsettings.json` is deleted before any new-product action can read it. That is why
  `ReadSettings` exists, and why approach A moves the removal.
- Every component uses `Guid="*"` (keyed on the target path) except `PathEnvironment`. The
  `AppSettings` component keys on `appsettings.json` in `INSTALLFOLDER` in both v0.22.0 and now,
  so its GUID is the same across versions. Late removal depends on this for every component.
- `src/appsettings.json` is the one shared file every host copies to its publish output. The CLI,
  LSP, TUI and Orchestrator load it with `AddJsonFile("appsettings.json")`; the Portal through the
  `WebApplication` defaults. All layer `appsettings.secrets.json` with `AddInstalledSecrets`.
- `BackupRestoreService`, `DataPurgeService`, `EngineRunner` and `SecurityService` read
  `appsettings.json` directly by name.
- `Test-MsiPortalUpgrade.ps1` asserts kept secrets, the kept `UpgradeSentinel`, secrets moved out
  of `appsettings.json` (the test writes them there after the v0.22.0 install), and no first-run
  file on upgrade.

## Approaches considered

| | Approach | Trade-off |
| :--- | :--- | :--- |
| **A (chosen)** | Late `RemoveExistingProducts`; `appsettings.json` `NeverOverwrite`; defaults in `appsettings.defaults.json`; registry for installer choices; services do the rest. | No custom actions at all. Depends on stable component GUIDs across versions; the MSI upgrade certification proves it. |
| B | Keep the early removal; replace the JScript with one compiled C# custom action that saves the settings; services do the rest. | Lower MSI risk, but keeps a LocalSystem custom action: the MSI does not just copy files. Fallback if A fails certification. |
| C (rejected) | Operator file from v0.23.0 on; v0.22.0 installs lose non-secret edits once. | Owner: upgrades must keep operator edits. |

Owner chose A, 2026-11-21. Owner decided upgrades keep operator edits to `appsettings.json`,
including from v0.22.0.

## Design

### 1. Settings layers (all hosts)

One extension in `ETL-SQL.Core` (`AddEtlSqlSettings(baseDirectory)`) replaces the per-host
`AddJsonFile("appsettings.json")` calls, lowest to highest:

1. `appsettings.defaults.json` — optional; present only in an MSI install.
2. Installer registry values (Windows only; absent elsewhere) — see §3.
3. `appsettings.json` — the operator's file (in non-MSI layouts, still the full defaults).
4. `appsettings.{Environment}.json` where a host loads it today.
5. `appsettings.secrets.json` (`AddInstalledSecrets`, unchanged placement rule).
6. Environment variables, command line, then `AddSecureConfiguration` as today.

The direct readers listed above resolve settings through the same layers (or the same helper),
not by reading `appsettings.json` alone. Backup and restore carry the operator file and the
secrets file as today; the defaults file is part of the package, not the backup.

### 2. MSI layout and schedule

- `MajorUpgrade Schedule="afterInstallExecute"`.
- The MSI build stages the published `appsettings.json` as `appsettings.defaults.json` (new
  component, normal overwrite) and installs a minimal operator `appsettings.json` (`{}`, no
  comment, so every JSON reader including PowerShell parses it) in the existing `AppSettings` component, marked
  `NeverOverwrite="yes"`, same Id and path so the auto-GUID matches v0.22.0.
- Remove the five custom actions, their sequence rows, `PREVIOUS_SETTINGS`, the `PortalJwtScript`
  component, `configure-portal-jwt.ps1` and `installer-actions.js`.
- Verify before relying on it: the v0.22.0 MSI's `Component` table GUIDs equal the candidate's for
  every component the two share (a check script, run in CI on the built MSI against the previous
  release MSI the certification already downloads).

### 3. Installer choices as registry values

The MSI writes `HKLM\Software\ETL-SQL\Install` with native `RegistryValue` elements, in the
components of the features they describe:

- `InstallFolder` = `[INSTALLFOLDER]` (also the install marker, §4)
- `Surface` inputs: `OrchSurface`, `StewardSurface`, `ReportPortal`
- `Modules`: `Reporting`, `Designer`, `Scheduling`, `Operations`
- `OrchestratorDatabasePath` = the LocalSystem profile path the script writes today

`RegistrySearch` reads each value back into its `INSTALL_*` property at `AppSearch`, so an upgrade
keeps the previous choices unless the command line sets them. (Today an upgrade without the
properties falls back to "All".) The registry provider maps the values to `Portal:Surface` (the
script's truth table moves to C#), `Portal:Modules:*`, `Portal:Orchestrator:DatabasePath` and one
`Security:ApprovedSafeZones` entry for the install folder. It sits below `appsettings.json`, so an
operator's explicit value wins. A v0.22.0 install has no registry values yet; its kept
`appsettings.json` already holds the values the script wrote, and the upgrade's own properties
write the registry for the next time.

### 4. First-start bootstrap (Orchestrator and Portal)

`InstalledConfigurationBootstrap.Ensure(baseDirectory)` in `ETL-SQL.Core`, called by both
services before they build configuration:

- Runs only when the registry `InstallFolder` equals the host's base directory. Otherwise returns
  without touching anything.
- Holds a machine-wide named mutex (`Global\ETL-SQL-InstalledConfiguration`) for the whole step,
  so the two services cannot race.
- Reads `appsettings.secrets.json` (if any) and `appsettings.json`. For every path in
  `ConfigurationExtensions.InstalledSecretPaths`: a value in `appsettings.json` moves to the
  secrets file (secrets file wins if both are set) and the operator file keeps an empty value.
- Generates any missing `Portal:Jwt:Secret`, `Portal:Dataset:AtRestKey`, `Orchestrator:ApiKey`,
  `Orchestrator:IdentitySigningSecret` (32 random bytes, base64), mirrors the API key and signing
  secret to `Portal:Orchestrator:*`, and generates the first-run admin password when there is no
  `portal.db` and no `first-run-password.txt` (same rules and format as the script).
- Writes the secrets file and `first-run-password.txt` through a handle opened with the final ACL
  (SYSTEM and Administrators only, protected), staged and replaced as `Write-ProtectedFile` does;
  the secrets file is written before the sign-in file. The operator file is rewritten only when a
  secret was moved out of it.
- Logs only fixed messages; never a value.
- A failure stops the service start with that message (Windows records the start failure).

### 5. The v0.22.0 operator file

A kept v0.22.0 `appsettings.json` holds every v0.22.0 default, so it shadows any default this
release changes. Owner-approved 2026-11-21: the bootstrap removes from the
operator file each leaf equal to the v0.22.0 shipped default (an embedded copy of the v0.22.0
`src/appsettings.json`), once, recording that it ran. The file is left with only real edits. An
operator who deliberately pinned a value equal to the old default loses the pin; that cannot be
told apart and is accepted.

### 6. Tests and certification

- Unit: the layer order; the registry provider's surface truth table (moved from the script
  tests); the bootstrap's move, generate, mirror, idempotence, the not-installed no-op, the mutex,
  ACLs, and the v0.22.0 slimming. Port the relevant cases from `InstallerConfigurationScriptTests`
  and keep its comparison of the secret path list against `build-linux-packages.sh`.
- Remove `test-installer-actions.mjs`; replace with a check that `Installer.wxs` has no
  `CustomAction` with `BinaryKey`/`JScriptCall`/`Script`, and has `NeverOverwrite` on `AppSettings`.
- `Test-MsiPortalUpgrade.ps1`: `Assert-Setting` resolves through the defaults file, the operator
  file and the secrets file; add "the v0.22.0 operator file is the one in place after upgrade",
  "no `configure-portal-jwt.ps1` left in the install folder" and "installer choices kept". Fresh,
  upgrade and rollback via `admin restore` all pass on the hosted MSI In-Place Upgrade run.
- Release notes and `BREAKING_CHANGES.md`: operators edit `appsettings.json` as before; the full
  defaults now live in `appsettings.defaults.json`.

## Calls made in this note (Claude's, for the owner to check)

- An Orchestrator-only install also generates the Portal secrets: one code path, harmless.
- The slimming in §5 records that it ran in the secrets file (`Installer:SlimmedFrom = "0.22.0"`),
  so it never runs twice.
- Values the v0.22.0 script wrote into `appsettings.json` (surface, modules, safe zone, database
  path) are left to §5: equal to the default, they are removed and the registry layer supplies
  them; different, they stay in the operator file and win.
- Uninstall during rollback removes the operator file (not `Permanent`); `admin restore
  --in-place` puts it back, as the certification already does.
