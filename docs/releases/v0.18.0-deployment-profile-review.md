# v0.18.0 Deployment Profile Review

The release review that
[Deployment_Profile_Standards.md](../architecture/standards/Deployment_Profile_Standards.md#release-review)
requires: for everything this release shipped, which profile is the smallest one where the
capability applies, how each larger profile accomplishes the same thing, and which cells are
genuinely **N/A** rather than an unstated Portal prerequisite.

Read alongside the [capability matrix](../architecture/standards/Deployment_Profile_Standards.md#capability-matrix),
which this review does not restate.

## The honest summary first

**v0.18.0 is a Portal and Enterprise release.** Most of what it added — Studio authoring authority,
governance workflow, the administrative diagnostic surfaces — has no Solo form, because Solo has no
Portal. That is a legitimate answer, not a gap, on one condition: *the underlying evidence must stay
reachable without the Portal*. This release keeps that condition. Every governance and quality
surface it added reads `eng.*`, which the CLI, the Report Player and the Orchestrator serve from the
same code, so a Solo operator sees the same rows through a different door.

Where that condition is **not** met, this review says so rather than colouring the cell green.

## 1. Studio authoring authority

Studio capabilities (deny-by-default, group- and service-account-assignable), the `Author` folder
grant, draft → review → publish, and protected branches.

| Profile | How the capability is accomplished |
| :--- | :--- |
| **Solo / Workstation** | **N/A, genuinely.** One trusted operator edits scripts in a text editor or the VS Code extension; the file system and source control are the boundary. There is nobody to separate duties *from*, and a review workflow with one participant is ceremony. |
| **Team / SME** | Portal Studio with capabilities assigned to groups. `Portal:Studio:RequireApprovalToPublish` is the smallest useful form of review, and it is **off by default** so an upgrade never interposes a step into a workflow people depend on. |
| **Enterprise / Corporate** | Adds protected branches (`Portal:SourceControl:ProtectedBranches`), service accounts capped by their owner's capabilities, and the `Reviewed-by:` commit trailer so the review outlives the Portal database — an auditor reads it from `git log`. |
| **SaaS / Multi-Organization** | **Not certified.** `ScriptIngress` is designed to be disabled in catalog-only SaaS, but tenant-scoped authoring boundaries are not proven. Do not infer support from the Enterprise path. |

**Portability check.** A `.rptsql` authored under any profile runs unchanged under the others.
Capabilities gate *who may author in the Portal*; they are not embedded in the artifact.

**Correction this release made.** An `Author` grant conferred `Manage` authority because
`FolderPermission` stores Author above Manage while ranking it below. Any deployment that had
issued Author grants should re-read them: an Author could publish new reports into that folder.

## 2. Data quality and quarantine remediation

Column rules, `ASSERT JOB`, quarantine capture, disposition and replay, the rule inventory, and
structured per-rule failure detail.

| Profile | How the capability is accomplished |
| :--- | :--- |
| **Solo / Workstation** | Complete without a Portal. `@expect`/`@fail` rules and `ASSERT JOB` run in the CLI; quarantine tables are written locally; `REPLAY QUARANTINE` is an engine statement, not a Portal feature. Evidence is `eng.data_quality_status`, `eng.data_quality_failures` and `eng.data_quality_rules`, plus the quality JSON the CLI emits and a non-zero exit code for gating. |
| **Team / SME** | Adds durable history in the local Orchestrator: baselines, trends, and SMTP/webhook recovery notifications — [without requiring Portal](../guides/feature-guides/data-quality.md#running-unattended-without-portal). |
| **Enterprise / Corporate** | Adds the Portal steward queue: row preview under the caller's execution identity with RLS, timeout, row cap and redaction intact; disposition and replay tracked to a terminal state with a durable submission record; every raw row read audited as a data-access event. |
| **SaaS / Multi-Organization** | **Not certified** — tenant isolation of quarantine tables, manifests and preview connections is not proven. |

**Deliberate boundary.** Row preview is gated by `Portal:DataQuality:AllowConnectionPreview`,
**default off**. Reading quarantined rows means reading whatever PII the source carried, so the
capability is opt-in per deployment rather than implied by holding a steward role.

## 3. Governance workflow

Findings, decisions, glossary, badges, scans, scoring settings, and the stewardship/protected-data
inventories.

| Profile | How the capability is accomplished |
| :--- | :--- |
| **Solo / Workstation** | `etlsql scan --pii`, the stewardship component scores in `eng.stewardship_score`/`eng.stewardship_gaps`, protected-data inventory in `eng.protected_data`, and the source-controlled `etlsql-policy.json`. Scoring is **policy-driven and versioned**, so the number is reproducible on a workstation and in CI. |
| **Team / SME** | The same scores, with history so a trend exists. |
| **Enterprise / Corporate** | The Portal governance dashboard adds workflow — assignment, review, decisions, glossary, badges — over durable models, with authorization and a security audit on every mutation. |
| **SaaS / Multi-Organization** | **Not certified.** |

**A discrepancy worth knowing about.** The Portal governance dashboard scores assets with a
configurable *deduction* model (`GovernanceScoringSettings`). `eng.stewardship_score` computes
*weighted component coverage* from the workspace policy. They answer different questions and will
not agree. If you compare them, compare them knowingly — the `eng.*` figure is the portable one.

## 4. Administrative diagnostics and posture

Identity diagnostics, credential and dataset-key posture, operations posture, policy-authority
impact, audit-collector health, support bundle, access simulator, environments plan/validate, and
the read-only fleet workspace.

| Profile | How the capability is accomplished |
| :--- | :--- |
| **Solo / Workstation** | `etl-sql doctor` for configuration and driver checks; `etl-sql admin support-bundle` for host files and configuration the Portal cannot reach. Most posture endpoints are **N/A**: they answer questions about a shared deployment that a single workstation does not have. |
| **Team / SME** | The Portal surfaces apply as soon as there is a Portal, and are most useful for the ones that compare two sources of truth — credential posture (which connections reference which secrets) catches a failure invisible on either page alone. |
| **Enterprise / Corporate** | The full set, including fleet visibility across environments. Naming an environment grants **visibility, never authority**: one scoped read-only GET per environment and nothing else. |
| **SaaS / Multi-Organization** | **Not certified**, and the fleet design explicitly does not approve remote mutation. Any future proposal needs its own threat model — see [Enterprise Security Review Packet](../architecture/decisions/Enterprise_Security_Review_Packet.md#remote-fleet-mutation-non-approval). |

**Recovery stays on the host in every profile.** The Portal reports backup freshness and
restore-drill evidence; it never holds custody and never performs the restore. That boundary does
not move as the profile grows.

## 5. Authorship is not permission

Dataset grants at registration, per-user dataset ACLs, delivery-time re-authorization for
subscriptions and alerts, and directory/group removal revocation.

| Profile | How the capability is accomplished |
| :--- | :--- |
| **Solo / Workstation** | **N/A, genuinely.** One operator; there is no second principal for a grant to outlive. |
| **Team / SME** | Applies in full the moment a second person exists. This is the smallest profile where the rule has meaning, and it is where the defect it fixes would first bite: an alert continuing to push data to its author after they lost access. |
| **Enterprise / Corporate** | Adds directory-driven revocation: group removal takes the report, its saved views and its anonymous share links, while a grant made to you *personally* deliberately survives losing a group. |
| **SaaS / Multi-Organization** | **Not certified.** |

## 6. Portal interface quality

Accessibility, responsive behaviour, the shared state vocabulary, navigation, and asset caching.

Not profile-varying: wherever the Portal runs, it renders the same way. Recorded here only so the
review is complete, and because two items have operational consequences worth knowing:

- Static assets are now revalidated rather than refetched, cutting roughly 3.4 MB per page
  navigation. This matters most on constrained or remote links, which correlates with smaller
  deployments rather than larger ones.
- `Portal:Topology:ExpectedMode` defaults to `Auto`, which infers `HighAvailability` from PostgreSQL
  **or** a configured key-ring path and never infers `Departmental`. A Team deployment on PostgreSQL
  is therefore classified HA and held out of load-balancer rotation until told what it is. Set it
  explicitly on anything that is not a plain single-node install.

## Matrix cells this release changes

Per the standard, a release claim names the cells it moves. This release does **not** move any cell
to Green that was not already there. It strengthens evidence behind existing Green cells
(Quality/stewardship, Audit, Observability at Enterprise) and adds acceptance lanes that make those
claims re-testable — browser, accessibility, responsive, local/Docker parity, departmental
isolation, role/module/capability, and policy journeys are now gate phases.

The SaaS column is unchanged and remains **Red** for every concern this release touched. Nothing
here was certified against a mutually untrusted tenant boundary, and the Enterprise happy path is
not evidence that it would hold.

## Current certification ledger

The release candidate must run both aggregate certification commands from a clean worktree:

```powershell
./scripts/Test-DeploymentProfileCertification.ps1 -Profile All -ReleaseVersion 0.18.0
./scripts/Test-DeploymentProfileCertification.ps1 -Transition All -ReleaseVersion 0.18.0
```

The stable release ledger is retained at
`artifacts/release-evidence/0.18.0/deployment-profiles/claims-index.md`; its JSON companion is the
machine-readable source. A claim is current only when its row is `Passed`, `releaseEligible` is
`True`, and the linked bundle names the exact candidate commit. The profile run records Solo, Team,
Enterprise, and **Managed Dedicated SaaS** separately. The transition run records Solo → Team,
Team → Enterprise, Enterprise → Managed Dedicated, Solo → Managed Dedicated, and the four-profile
N → N+1 upgrade proof.

Shared SaaS remains `NotCertified`. It has no row that can turn Green from these lanes; its hostile
shared-control-plane and hardened execution evidence remains future work.
