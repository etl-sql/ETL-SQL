# v0.20.0 Performance Results — Scale Harness Investigation

**Status:** Development evidence. Clean-commit baseline calibration and final release certification
remain open. The measurements below come from `803ff4227a8d0da174f8dc77bf51ecaf4b5c145e` plus
the working tree on 2026-10-03. They are not release-candidate certification or an engine speedup claim.

## Output capture dominated the streaming measurement

The streaming scenario processes 1,000,000 source rows, retains 50,000 result rows and formats the
entire retained result while its stopwatch runs. A diagnostic sink counted five output writes and
850,160 characters. The same Release binaries, rows, formatter and correctness checks were used
with three capture methods:

| Capture method | Samples | Median scenario time | Median output-write time |
| :--- | ---: | ---: | ---: |
| Existing `Start-Process -RedirectStandardOutput` | 3 | 4,880 ms | 4,726 ms |
| Concurrent buffered byte-stream capture | 3 | 553 ms | 391 ms |
| Discard writes after formatting, diagnostic only | 2 | 148 ms | <0.1 ms |

Output writes consumed about 97% of the old runner's measured time. The buffered runner retains
the complete formatted output; discarding output is prohibited in certification. Separate capture
tests verify both stdout and stderr byte-for-byte with large UTF-8 payloads, spaces in child paths,
blank lines and nonzero child exits.

The Windows redirection implementation opens output handles with `FileOptions.WriteThrough`.
This exposes the scenario timer to physical write latency. The Unix implementation uses a different
line-handler path, so the Windows finding must not be described as a Unix result.
See [PowerShell 7.6.6 source](https://github.com/PowerShell/PowerShell/blob/v7.6.6/src/Microsoft.PowerShell.Commands.Management/commands/management/Process.cs#L2181-L2186).

This identifies a measurement dependency large enough to explain the historical streaming band
failure. It does **not** identify which storage, OS or security-filter change made that dependency
slower between August and September. The old reference is retained until a known-good clean commit
has been calibrated with the corrected fixture. Comparing old and new capture methods is refused.

Raw logs are under `artifacts/performance-investigation/20261003-output-probe/`.

## Runtime patch control

The test host's framework version was pinned in an interleaved 10.0.12/10.0.11/10.0.11/10.0.12
sequence, with the runtime configuration restored afterward. The binaries, formatter and direct
native file capture were otherwise unchanged.

| Actual test-host runtime | Scenario times | Median |
| :--- | :--- | ---: |
| .NET 10.0.12 | 543, 554 ms | 549 ms |
| .NET 10.0.11 | 547, 558 ms | 552 ms |

The 0.6% delta is smaller than either arm's roughly 11 ms spread. This probe does not support a
runtime-patch explanation for the streaming drift; it says nothing about other scenarios.
Raw logs are under `artifacts/performance-investigation/20261003-runtime-probe/`.

## Test discovery also changes the measurement fixture

The first full Standard run with buffered capture passed all 13 scenarios in each of five samples.
External sort's median GC pause remained 243 ms against the historical 133 ms. Elapsed time was
4,522 ms against 4,436 ms; the GC observation did not establish an algorithmic regression.

An isolated external-sort probe used the same assembly with theory pre-enumeration enabled,
disabled, disabled, enabled. The enabled arms began at 296/237 MB working set and recorded
191/204 ms GC pause. Disabled arms began at 196/196 MB and recorded 121/166 ms. Timing was noisy.
This shows that unrelated theory discovery affects the retained starting heap and measured GC;
it is not a five-sample calibration or proof that every historical GC difference has one cause.
Raw reports and the assembly hash are under
`artifacts/performance-investigation/20261003-discovery-probe/`.

Scale certification now passes `PreEnumerateTheories=false` through its own runsettings file.
Selected theories still execute their data rows. This removes unrelated eager data enumeration from
the scale fixture and does not change the ordinary test lanes. The baseline comparator rejects
different enumeration settings. See [xUnit runsettings documentation](https://xunit.net/docs/config-runsettings#preenumeratetheories).

The revised full Standard run passed all 65 measurements. External sort began at 176–204 MB,
with 4,035 ms median elapsed time and 142 ms median GC pause (112–222 ms range). This brings the
median pause near the historical 133 ms while preserving all row, checksum and memory checks.
It supports correcting the fixture before calibration, not an engine optimization claim.
Reports are under `artifacts/performance-investigation/20261003-deferred-standard/`.

## Corrected runner and remaining work

- Capture both output streams concurrently through buffered files, then wait for complete drains.
- Record the actual test-host runtime and measurement configuration.
- Use a run-owned temporary directory and spill cleanup; never delete another run's shared spill
  root or kill unrelated test hosts.
- Refuse diagnostic output suppression, stale binaries, missing metrics and incomplete samples.
- Keep the discarded process as file-cache priming. Every measured process retains its own JIT and
  tiered-compilation startup; it is not an in-process JIT warm-up.

The five-sample isolated streaming verification passed correctness and memory checks with
547–570 ms scenario times. The earlier full Standard verification passed 65 measurements under
`artifacts/performance-investigation/20261003-buffered-standard/`. Both are dirty-worktree
development records. Deferred-discovery Standard also passed 65 measurements. Clean-commit
Smoke/Standard calibration and candidate comparisons remain required.
No checked-in baseline has been replaced by these development runs.
