## R01 — P0: tool output silently changes large integers

Location: [ExecuteToolStatementHandler.cs](../../src/ETL-SQL.Engine/Handlers/ExecuteToolStatementHandler.cs), line 541.

The JSON numeric branch uses `je.TryGetInt64(out var l) ? l : je.GetDouble()`. The conditional expression promotes the successful integer branch to double before the expected-schema conversion. Integer values beyond exact double precision lose information; fractional decimal values also pass through double.

**Reproduced through the actual handler's StreamOutputAsync method:** JSON output `{"n":9007199254740993}`, with expected schema `n BIGINT`, produces decimal `9007199254740990`. The output correctness assertion fails. A tool can therefore return a correct identifier and ETL-SQL can load a different identifier into the destination.

Fix: preserve integer and decimal representations according to the declared type; reserve floating-point conversion for floating-point types. Add behavior tests for large integers, decimal precision, negative values, and numeric boundaries. The deterministic reproducer is included below.

## R02 — P1: last-mile log redaction leaks secret content

Locations: [SecretRedactor.cs](../../src/ETL-SQL.Core/Common/SecretRedactor.cs), lines 41–46; [LoggerService.cs](../../src/ETL-SQL.Infrastructure.Logging/LoggerService.cs), line 145.

The assignment and JSON regular expressions stop at whitespace even inside quoted values. Without a matching runtime-secret registration, both `PASSWORD='synthetic first second';` and `{"password":"synthetic first second"}` retain the secret suffix `first second`.

LoggerService also returns non-string objects unchanged from RedactLogArgument. Logging an anonymous object with a Password property writes the synthetic password to the file.

**Both reproduced.** This affects the protection offered by the logging boundary, including provider errors whose secret values were not registered. Runtime registration does not repair the general quoted-value/object handling.

Fix: redact complete quoted values, including escaped quotes, and establish a safe policy for object arguments before formatting or destructuring. Test final file output, not just helper return values.

## R03 — P1: container tool secrets are exposed in command-line arguments

Location: [ExecuteToolStatementHandler.cs](../../src/ETL-SQL.Engine/Handlers/ExecuteToolStatementHandler.cs), lines 131–144.

CAPABILITY_SECRETS are decrypted and appended as `docker run -e NAME=plaintext` arguments. This exposes the value through host process-command-line inspection and any process telemetry that records arguments. Log redaction cannot protect the OS argument list.

Fix: use an approved secret-delivery mechanism that does not put the value in argv. If environment forwarding is appropriate for the threat model, pass only the variable name to Docker and place its value in the controlled child environment. A mounted, protected secret file can provide a narrower lifecycle. Validate argument construction with synthetic secrets.

## R04 — P1: orphan cleanup can kill an unrelated process after PID reuse

Location: [ChildProcessTracker.cs](../../src/ETL-SQL.Orchestrator/Execution/ChildProcessTracker.cs), lines 64–68 and 161.

The persisted identity contains only PID and script path. On restart, CleanupOrphans opens that PID and kills its entire process tree without checking process start time or executable identity. If the original child exited and its PID was reused, the newly assigned process is killed. The service invokes this cleanup during startup.

Fix: persist and verify process creation identity, executable identity, and ownership before termination. Treat a mismatch as stale metadata and log the decision. Test with a fake process abstraction; do not exercise this against arbitrary live processes.

## R05 — P1: Portal service logs do not reach its configured application log files

Location: [Portal Program.cs](../../src/ETL-SQL.Portal/Program.cs), lines 60–70.

The Portal creates LoggerService and registers it for ETL_SQL.Common.ILogger. It does not register that file sink as a Microsoft.Extensions.Logging provider. Portal controllers and background services use ILogger<T>, so their operational errors follow the host's default logging providers instead of Logging:AppLog:Directory.

For example, audit transport sweep failures and database migration errors do not go through the configured engine file logger. External stdout collection may retain them, but that does not fulfill the configured local-file behavior, especially for a Windows service.

Fix: connect the host logging pipeline to a configured durable sink. Preserve tenant, correlation, run/attempt, node, and exception fields; apply a consistent sanitization boundary. Validate with a real host test that emits an ILogger<T> event and checks the resulting file.

## R06 — P1: tool execution ignores cancellation of the enclosing run

Location: [ExecuteToolStatementHandler.cs](../../src/ETL-SQL.Engine/Handlers/ExecuteToolStatementHandler.cs), lines 269–290.

The handler creates a timeout-only CancellationTokenSource. It does not link context.CancellationToken. Catalog resolution also uses CancellationToken.None. Cancelling an in-process run therefore does not cancel the handler's streams or process wait; work may continue until the catalog-defined timeout.

Fix: link the execution token and timeout, distinguish user cancellation from deadline expiry in the event record, and terminate/await the tool on all exceptional exits. Cover cancellation during input, output, and process wait.

## R07 — P1: timing out a container tool kills the Docker client, not the container

Location: [ExecuteToolStatementHandler.cs](../../src/ETL-SQL.Engine/Handlers/ExecuteToolStatementHandler.cs), lines 97–108 and 292–296.

The CONTAINER path launches docker run, then handles timeout with process.Kill(true). The daemon-managed container is not a child process of the Docker CLI. The handler has no container ID/name and does not issue a stop/remove request or verify detachment. --rm only removes the container after the container exits; it does not guarantee termination when its client is killed.

A timed-out tool can therefore continue running and using its mounted capabilities.

Fix: use a server-owned container identity and an explicit bounded teardown that proves removal, including failed starts and stream failures. Record teardown failures as actionable operational events. This was source-reviewed; no Docker fault test was run.

## R08 — P1: tool stderr can exhaust host memory outside the output limits

Location: [ExecuteToolStatementHandler.cs](../../src/ETL-SQL.Engine/Handlers/ExecuteToolStatementHandler.cs), lines 274–282 and 510–524.

Standard error is appended to an unbounded StringBuilder. Tools:Limits:MaxBytes only applies to parsed stdout rows. A noisy or malfunctioning registered tool can consume host memory through stderr until the time limit. ReadLineAsync also allocates a complete line before the stdout size check runs.

Fix: bound captured stderr and line lengths, retain a useful bounded diagnostic head/tail, and log truncation with run and tool identity. Drain or terminate consistently so the cap does not introduce a pipe deadlock. Configure operational limits in appsettings.

## R09 — P2: sandbox workspaces have no recovery cleanup after host restart

Locations: [SandboxWorkspaceProvider.cs](../../src/ETL-SQL.Orchestrator/Execution/SandboxWorkspaceProvider.cs), lines 111–112, 197–211, and 297; [SandboxAdmissionReconciliationService.cs](../../src/ETL-SQL.Orchestrator/Execution/SandboxAdmissionReconciliationService.cs), RunOnceAsync.

Workspace deletion requires an entry in the provider's in-memory _active dictionary and the assignment ownership token. Those live objects disappear on a host crash. Reconciliation probes/removes the runtime and releases retained admission capacity, but does not recover or delete the associated workspace. No workspace scavenger was found in the reviewed production paths; the allocation-failure comment explicitly defers to a later scavenger.

Input, capability, and output files can survive crashes indefinitely. Normal successful teardown does remove the workspace.

Fix: persist sufficient server-owned assignment/recovery metadata and reconcile workspace cleanup only after proven runtime detachment. Emit retained-residue and cleanup-result events with tenant/run/attempt identifiers. Never delete solely based on age.

## R10 — P2: disabling the audit collector also disables outbox cleanup

Locations: [AuditOutboxTransportService.cs](../../src/ETL-SQL.Portal/Services/AuditOutboxTransportService.cs), lines 24–32; [AuditService.cs](../../src/ETL-SQL.Portal/Services/AuditService.cs), Stage.

ExecuteAsync returns immediately when TransportEndpoint is blank, so PruneAsync never runs. AuditService still creates an AuditOutboxMessage for every staged audit event. Even a configured OutboxMaxBytes is consequently unenforced in this mode. AuditRetentionService deletes AuditLogs, not outbox rows; their relationship uses SetNull.

Fix: separate local queue maintenance from transport enablement, or define explicit no-collector queue behavior. Keep durable audit retention independent. Test the hosted service with no collector and a small outbox cap.

## R11 — P2: network exceptions bypass audit retry accounting

Location: [AuditOutboxTransportService.cs](../../src/ETL-SQL.Portal/Services/AuditOutboxTransportService.cs), lines 76–108 and 372–390.

The batch is claimed before PostBatchAsync. If sending throws a DNS/TLS/connection/timeout exception, the outer catch records telemetry and rethrows; it never calls ApplyFailure. Attempts and LastError remain unchanged and the claim stays locked until expiry. The next send follows lock expiration rather than the configured retry/backoff policy, and TransportMaxAttempts is never reached for repeated exceptions.

Fix: handle transport failures against the claimed batch, persist a sanitized error and retry state, and release the claim. Preserve shutdown cancellation semantics. Add exception-path tests alongside the existing HTTP-status tests.

## R12 — P2: audit collector HTTP failures have no warning/error log event

Location: [AuditOutboxTransportService.cs](../../src/ETL-SQL.Portal/Services/AuditOutboxTransportService.cs), lines 87–105 and 372–390.

An HTTP 401/403/500 response updates outbox state and telemetry but emits no warning or error. Reaching terminal Failed also emits no log. Thus an administrator reading operational logs cannot see credential rejection or exhausted delivery attempts from this path; a backlog warning only appears if its separate count threshold is crossed.

Fix: log a sanitized status, affected batch/event count, attempt, next retry, and terminal transition. Include tenant/batch correlation without including audit payloads or bearer credentials. Rate-limit repetitive warnings while preserving terminal failures.

## R13 — P2: every engine app-log event is written twice

Location: [LoggerService.cs](../../src/ETL-SQL.Infrastructure.Logging/LoggerService.cs), lines 111, 125, and 173–174.

WriteCore writes directly to _appLogger and then to _msLogger. InitializeAppLogger constructs that MEL logger from the same _appLogger. A single Info call therefore produces two file events; the second copy also goes through preformatted text.

**Reproduced:** one marker-producing call yielded two matching log lines. This doubles file traffic and inflates any event counts derived from those logs.

Fix: choose one route to the application sink. Preserve structured properties through that route. Add a file-output assertion for one event per call.

## R14 — P2: Orchestrator host file logging bypasses application logging settings

Location: [Orchestrator.Service Program.cs](../../src/ETL-SQL.Orchestrator.Service/Program.cs), lines 55–58, 70–76, and 98–102.

The service hard-codes a host sink at logs/orchestrator-.log in both bootstrap and final logging configuration. Separately, engine logging reads Logging:AppLog:Directory, RetentionDays, and FileSizeLimitMb. Changing those settings does not move or bound the hard-coded host sink, and adding configured sinks does not remove it.

Fix: give host and engine logging one documented configuration contract, including path, size rolling, retention, minimum level, and structured format. Keep bootstrap logging explicit, then replace it with the final configured pipeline. Test relocation and rollover. Fixed operational policy belongs in configuration; protocol constants and buffer sizes do not all need new settings.

## R15 — P2: operational metrics load entire pending audit payloads into memory

Location: [OperationalMetricsService.cs](../../src/ETL-SQL.Portal/Services/OperationalMetricsService.cs), lines 178–182.

GetAsync materializes every pending audit row's CreatedAt and PayloadJson merely to calculate backlog diagnostics. During the collector outage this screen is intended to diagnose, that list grows with the full pending payload volume. Concurrent calls multiply the allocation. The method also materializes all recent duration pairs and pending job timestamps.

Fix: calculate count, oldest timestamp, and payload-size aggregates in the database; similarly aggregate durations/queue age where supported. Keep tenant filtering intact. Validate allocation/query behavior with a large synthetic backlog. No load benchmark was run in this review.

## R16 — P2: cancelled PDF image writes can leave untracked temporary files

Location: [PdfExporter.cs](../../src/ETL-SQL.Reporting/PdfExporter.cs), lines 381–383, 564–566, and 655–657.

Temporary image paths enter tempFiles only after WriteAllBytesAsync succeeds. A cancellation or write failure after creating a partial file skips registration, so the outer finally cannot delete it. Deletion errors for registered files are also swallowed without a log.

Fix: register the owned path before writing, or use a per-export owned temporary directory and a logged cleanup helper. Test cancellation/failure after file creation. Report imagery may contain user data, so leftover files are more than disk clutter.

## R17 — P2: Gateway outcome persistence grows without bound and rewrites all history

Location: [GatewayOperationProtocol.cs](../../src/ETL-SQL.Core/Governance/GatewayOperationProtocol.cs), lines 170, 215–257, and 319–328.

The production durable GatewayOutcomeLedger keeps every outcome in a dictionary. Each dispatch and terminal transition serializes the entire dictionary to a new file under the global lock. There is no retention or compaction path. With N retained operations, one transition costs O(N) serialization/write work and cumulative lifetime write volume grows approximately quadratically.

Fix: use incremental durable storage and indexed lookup, with a defined replay-retention contract. Do not simply delete old mutating outcomes: their receipts prevent replaying writes. Expose operational retention/compaction policy in configuration and measure behavior at realistic history sizes.
