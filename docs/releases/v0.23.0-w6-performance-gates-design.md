# W6 Performance Certification Redesign (v0.23.0 design note)

**Status:** Approved by the owner, 2026-11-18 (all four decisions as written). Covers TODO §3.5 (W6), §1.9 (spill GC-pause
gap) and §2.8 (scale baseline recalibration).

## Summary

- Gate hard on what the engine *does*, not how fast one machine did it: correctness, work counters
  (spill bytes, extents, partition passes, plan decisions), allocated bytes, and the absolute
  memory cap.
- Gate timing in one place only: a same-runner, interleaved A/B (ABBA) run of the release candidate
  against the previous release, once per release.
- GC pause, GC counts, elapsed time and throughput become report-only everywhere else.
- Baselines move from the owner's workstation to hosted `ubuntu-latest` captures, made by a
  dispatchable workflow. The first capture re-lands `8b50435fe` (§2.8).
- §1.9 closes by policy: GC pause is a machine metric and stops gating.
- No waivers. A failure is fixed, or the baseline is recalibrated in a commit that says why.

## Problem

Today there is no performance gate in the release path at all:

| Where | What gates | Timing |
| :--- | :--- | :--- |
| CI `engine-certification` (every push) | Rows, checksums, failed scenarios | Report-only: compared to the workstation baseline with `-PerformanceReportOnly` |
| Spill allocation profile (CI) | Bytes per row | GC counts, pause, peak report-only (`-MachineMetricsReportOnly`) |
| `release-evidence.yml` scale tiers | Rows, checksums (`-Samples 1`) | None |
| `Test-PreRelease.ps1` (workstation) | Everything, including elapsed and GC pause | Hard, against workstation baselines |

Releases now go only through GitHub Actions, so the only hard timing gate is on a machine whose
results are not release evidence. That gate is also what keeps §1.9 open: the four Smoke spill
gaps are 5–30 ms GC-pause differences.

The baselines are fragile too. `Assert-ScaleCaptureCompatibility` refuses any comparison when the
scale test fixture hash changes, so a one-line test fix (`8b50435fe`) broke both baseline checks
and had to be reverted (§2.8).

## Evidence: which metrics are stable

Workstation baseline (`baseline-*.json`: Windows, 24 cores, .NET 10.0.13, commit `040d2c217`,
2026-10-23, 10 samples) against hosted CI run
[43957365297](https://github.com/etl-sql/ETL-SQL/actions/runs/43957365297) (Ubuntu, 4 cores,
.NET 10.0.15, commit `5d10fa781`, 2026-11-16, 3 samples):

| Metric | Within one run | Workstation vs hosted (different code, OS, runtime) |
| :--- | :--- | :--- |
| Rows, checksum | Identical | Identical |
| Spill bytes, extents, partition passes (not `spillReadBytes`; see slice 1) | Identical in every sample (10/10, 3/3) | Equal for 9 of 13 Smoke scenarios; join, sort, window and scalar-subquery differ (code changes since `040d2c217` and machine are confounded) |
| Allocated MB | ≤2.7% spread | +1% to +5%, except Standard `CubeGroupingSets` +18.7% |
| Gen-2 GC count | — | 0→2, 1→5, 8→4: no pattern |
| GC pause | — | Up to 7× (e.g. `SpillCleanupSuccess_50000` 4.8 → 34.3 ms) |
| Elapsed | Up to 72% spread on short scenarios; 4–9% on Standard scenarios ≥ 2 s | 1.4× to 3× |

Conclusions:

1. Work counters are deterministic for a given commit and environment. They can gate on exact
   equality, provided the baseline comes from the same environment class (hosted).
2. Allocations travel well across machines. A ±5% band is about twice the observed noise.
3. GC pause, GC counts and elapsed time can't be compared across machines, or even across runs on
   shared runners without pairing. They can only gate in a paired, same-runner comparison.
4. **Resolved in slice 1** (below): the Standard `CubeGroupingSets` +18.7% allocation growth is either a real
   regression since `040d2c217` or a scale-dependent nondeterminism. It must be explained before
   the hosted baseline is captured; otherwise the recalibration would bless it.

## Slice 1 results (2026-11-18)

Five independent `ubuntu-latest` replicas of Smoke and Standard (5 samples each) plus the spill
allocation profile, all at commit `b520fba4f`
([run 44383241458](https://github.com/etl-sql/ETL-SQL/actions/runs/44383241458),
`.github/workflows/perf-calibration.yml`):

| Metric | Result across 25 samples per scenario | Consequence |
| :--- | :--- | :--- |
| Rows, checksum, spill write bytes, total spill bytes, extents, partition passes, plan counts | Identical in all 26 scenarios | Exact gate confirmed |
| `spillReadBytes` | Varies in 4 scenarios (aggregate, join, cube, both tiers) | Not a work counter: `SpillStore.CreateReaderAsync` adds the file's length when a reader opens, which is timing-dependent and well below bytes written. Report-only; fix the counter separately |
| Allocated MB, replica medians | ≤ 1.2% spread in every scenario | +5% fail band is about 4× noise; gate on the median of 5 samples |
| Allocated MB, single samples | ≤ 4.2%, except one Standard cube sample at +19% (4,759 MB vs 3,982–4,026 MB) | Never gate on one sample |
| Spill allocation profile | 594.7–595.0 bytes/row (0.1%) | Gate as today, tighter band possible |
| Elapsed, replica medians | 13–99% spread; 34–45% even for Standard scenarios ≥ 2 s | Cross-run timing is unusable; only same-runner A/B can gate |
| GC pause, replica medians | 19–83% spread | Report-only confirmed |

The open cube item is resolved. The baseline commit `040d2c217` allocated anywhere from 2.2 to
4.4 GB for the Standard cube on one machine (97% sample spread), so the +18.7% was measured
against a noisy reference. At HEAD, both hosted runners and the workstation measure about
4,000 MB, so cube allocations transfer across machines; the earlier 4,443 MB hosted figure came
from an older commit. The rare single-sample outlier means cube must gate on the median. The
plan decision count changed from 4 to 5 between those commits, which is exactly the kind of work
change the exact gate exists to surface.

## Design

### Metric classes

| Class | Metrics | Rule | Where |
| :--- | :--- | :--- | :--- |
| Correctness | Scenario passed, result rows, checksum | Exact; always fails | Everywhere (unchanged) |
| Work | Spill bytes, spill write bytes, extent count, partition passes, plan decision/fallback/rejected/degraded counts | Exact equality with the hosted baseline | CI `engine-certification`, release evidence |
| Allocation | `allocatedMB` per scenario; spill-profile bytes per row | Fail above +5%; warn above +2%; warn below −10% (prompts a ratchet recalibration) | Same |
| Memory cap | `memoryPassed` (peak under `memoryBoundMB`) | Absolute; always fails | Everywhere (unchanged) |
| Machine | Elapsed, rows/s, GC pause, GC counts, CPU time, peak working set vs baseline | Report-only | Everywhere except the A/B job |
| Paired timing | Candidate/base elapsed ratio per ABBA block | See below | Release evidence only |

A work-counter difference means the engine now does different work. That is either a bug or an
intended change. If it is intended, the same change recalibrates the baseline and the commit says
why. Exact equality is turned on only after slice 1 shows five hosted runs agree. A counter that
varies between runs is a nondeterminism bug to fix, not a reason to widen the rule.

### Paired timing (ABBA)

- **When:** once per release candidate, in `release-evidence.yml`, which follows the owner's
  "run heavy certs once per release" rule.
- **What:** the candidate commit (B) against the previous release tag (A), built on the same
  runner. Only scenarios present in both with the same row count and checksum are compared.
- **How:** each gated scenario runs in A, B, B, A order for at least 5 blocks in one job, using
  the existing per-scenario process isolation and discarded warm-up. Each block yields one
  candidate/base ratio, so runner drift cancels within the block.
- **Gate:** fail when the median block ratio is above 1.15 *and* at least 4 of 5 blocks are
  above 1.0. Report the ratio and every sample.
- **Scope:** Standard-tier scenarios with a hosted median of at least 2 s (7 of 13 today, each
  with 4–9% sample spread). Shorter scenarios are report-only: their spread reaches 15–72%, which
  swamps a 15% threshold. Split into matrix jobs per scenario if one job would exceed about 60 minutes (sized
  in slice 3).
- **Calibration:** before the gate counts, an A-vs-A null run must show no failures. One
  deliberate slowdown on a throwaway branch must fail it.

### Baselines

- A new `workflow_dispatch` workflow, *Calibrate performance baselines*, runs Smoke and Standard
  with 5 samples on `ubuntu-latest`. It uploads `baseline-*.json` plus a diff report against the
  current baselines.
- Recalibration is a normal commit containing that artifact. The commit message states the reason
  and links the run. That commit is also where `8b50435fe` is re-applied (§2.8).
- The comparator drops the global fixture-hash refusal for work and allocation checks. They are
  keyed per scenario by name and row count, and a changed scenario shows up as its own diff. The
  fixture hash stays recorded, and still binds the A/B job, which builds both sides itself.
- Workstation baselines are retired (they stay in history). `Test-PreRelease.ps1` and local runs
  use the hosted baselines. Locally, only correctness and the memory cap fail; everything else is
  reported. Local runs are not release evidence.

### §1.9 and §2.8

- **§1.9 closes by policy.** GC pause becomes a machine metric. Real regressions show up as
  elapsed time in the A/B gate, or as allocation and GC-count growth in reports. The
  investigation note gets a closing section that records this decision and the hosted-vs-workstation
  table above.
- **§2.8** is done by the first hosted calibration commit, which carries `8b50435fe`.

## Decisions (approved 2026-11-18)

1. **Hard gate set:** correctness, exact work counters, allocation +5%, memory cap. GC pause, GC
   counts and elapsed time are report-only outside A/B.
2. **A/B:** candidate against the previous release tag, once per release, Standard scenarios
   ≥ 2 s, 15% median-ratio threshold.
3. **Baselines:** hosted `ubuntu-latest` captures replace workstation baselines; local runs gate
   only correctness and the memory cap.
4. **§1.9** closes by policy (GC pause is report-only), not by finding a root cause.
