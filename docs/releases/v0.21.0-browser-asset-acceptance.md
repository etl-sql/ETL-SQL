## Installed upgrades — 2026-10-17

`scripts/test-deb-upgrade.sh` installs packages on a systemd host (WSL Ubuntu 26.04) and checks what
runs and what a browser receives. The candidate DEB (0.20.1, `f52d9f05…`) was built from `90a3cf895`
with the installer changes below; the previous package is the released v0.20.0 DEB (`6f106a77…`).
All 33 checks passed (an earlier note said 37, which counted the NOTE lines too). Evidence:
`artifacts/deb-upgrade/evidence-pass-1/`. After the secrets moved to `appsettings.secrets.json`, a
DEB rebuilt from `5344e3e6a` passed all 37 checks, including four new ones. Fresh install and
upgrade both leave the file `640 root etlsql`, an unprivileged account can read
`appsettings.json` but not the secrets, and `appsettings.json` holds no generated secret
(`evidence-pass-2/`).

| Stage | Observed |
| :--- | :--- |
| Fresh install | Both services run the installed executables with no operator configuration; one-time sign-in is root-only (`600 root`); 343 served files match the inventory; purge removes state, cache and sign-in |
| Previous release | v0.20.0 needed the operator drop-in described below plus its documented first-start settings; served assets recorded as a browser cache; databases and configuration backed up with services stopped |
| Upgrade | Both services restarted on the new executables; JWT secret, API key, at-rest key and an operator setting kept; no new sign-in file; 343 served files match the inventory; revalidation: 160 changed files refetched, 16 unchanged, **0 stale 304** |
| Rollback | Previous package installed over the candidate, pre-upgrade backup restored; Portal healthy; previous assets served; 76 removed files answer 404; 0 stale 304 |

The served-asset check (`scripts/test-installed-portal-assets.mjs`) fetches every installed `wwwroot`
file. It ignores only the per-request CSP nonce and the byte order mark that the Portal's HTML
rewrite removes, and precompressed siblings negotiated on their original URL.
`scripts/checks/test-installed-portal-assets.mjs` proves it reports a stale 304, a reusable cache
policy, a tampered page and a served development file.

Defects found and fixed while getting it to pass:

1. **Linux services never started.** The `etlsql` system account has no home directory. Single-file
   extraction failed (status 159), then the security event outbox. The units now set
   `StateDirectory`, `CacheDirectory`, `HOME` and `DOTNET_BUNDLE_EXTRACT_BASE_DIR`. This affects every
   released DEB; v0.20.0 needed an operator drop-in to start at all.
2. **No installed Portal or Orchestrator could start out of the box (since v0.11.0).** The Portal
   needs a dataset at-rest key and a first-run password. The Orchestrator needs an identity signing
   secret. Both installers now generate them; the password goes to a root- or Administrators-only file.
3. **Upgrades replaced the configuration.** The JWT secret and API key were regenerated and operator
   settings lost. Both installers now carry the installed values forward and add only new keys. The
   MSI schedules the major upgrade `afterInstallInitialize` so a deferred action can keep the file.
4. **The DEB upgrade left the old executables running.** postinst now restarts the services.
5. **Packages shipped seven stray Portal snapshot files** with a build machine path. They are
   untracked, and the DEB build refuses a publish folder that holds runtime state.
6. **Rollback needs a database backup.** v0.21.0 renames the schema to snake_case, and v0.20.0 fails
   with `no such table: AspNetUsers` on a migrated database. Recorded in `BREAKING_CHANGES.md`.

Limits: the run used WSL rather than a clean VM. Rollback restores files rather than running
`etl-sql admin restore`. A workstation-only MSI upgrade still replaces `appsettings.json`. The
generated secrets were then still in `appsettings.json`, readable by every local user; they have
since moved to a protected `appsettings.secrets.json` (see the CHANGELOG security entry).

### First scan review — 2026-10-17

The changed workflow scanned `82bbea970`, `90a3cf895` and `b2608bc08`; both language jobs passed.
The release branch had 19 open alerts: 14 errors and 5 warnings.

| Alerts | Location | Disposition |
| :--- | :--- | :--- |
| #569, #570 `js/xss` | `rt-util.ts` `renderSafeSvgInto` | **Fixed.** Text that failed to parse as SVG was written with `innerHTML`, and parsed SVG kept its handlers. Now sanitized, with no markup fallback |

| #433, #434 `js/xss` | `rt-table.ts` sparkline and progress cells | **Fixed.** `td.innerHTML = micro.svg` replaced by the sanitizer |

| #432 `js/xss` | `rt-table.ts:532` hyperlink cell | False positive: `href` is assigned only when it matches `^https?://` |

`RuntimeSvgSanitizationTests` proves the fix in a real browser. A hostile SVG keeps its shapes,
text and internal `#` references, and loses script, `foreignObject`, animation, handlers and external
links. Four non-SVG or entity payloads write nothing. Its assertions inspect the DOM because the
Portal's CSP would block handlers either way. The browser regression suites (311 tests) and the
consumer gate pass. Dismissing the false positives on GitHub needs the repository owner.
