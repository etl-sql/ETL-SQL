# ETL-SQL v0.12.0

**Released:** 2026-06-19

ETL-SQL goes multi-node — run Portal and Orchestrator across a cluster of machines with database-backed coordination, automatic leader election, and fenced writes that prevent split-brain corruption.

---

## Release Summary

v0.12.0 delivers **Practical High Availability** by letting administrators scale the Portal and Job Orchestrator across multiple nodes backed by PostgreSQL. A database-backed coordinator handles leader election, heartbeat-based liveness, and monotonic fencing tokens that cancel in-flight work the instant a node loses its lease — eliminating the split-brain scenarios that plague home-grown clustering. New **Job-Scoped State Persistence** functions let scripts checkpoint progress and resume after restarts, while **JSON Schema Contract Checks** catch upstream data-shape drift before it silently corrupts downstream tables. This release also adds **Certified OIDC Authentication** for federated single sign-on and significant query-pushdown optimizations for cross-connection joins.

---

## ⚠️ Breaking Changes & Required Actions

- **Multi-node HA deployments have new infrastructure requirements.** Running more than one Portal or Orchestrator node now requires PostgreSQL (instead of SQLite), a shared artifact root (Local or SMB/UNC), a shared Data Protection key ring, identical JWT / orchestrator / dataset encryption keys across all nodes, and a load balancer with session affinity (sticky sessions). **Single-node SQLite deployments are not affected** — all defaults remain unchanged.

  **Action:** If you plan to enable HA, review the Upgrade Guide below and run a `--dry-run` migration before cutting over.

## Highlights

### Practical High Availability — Multi-Node Clustering

**Audience:** Administrators

**Problem:** Organizations running ETL-SQL in production had no supported path to eliminate single points of failure. If the Portal or Orchestrator host went down, reports were inaccessible and scheduled jobs stopped running until the server was manually recovered.

**Solution:** Both the Portal and the Job Orchestrator now support a provider-selectable database backend — choose between the existing single-node SQLite or enterprise-grade PostgreSQL. A new `RelationalJobHistoryStore` uses portable SQL so execution history, variable searches, and scheduling metadata work identically on both backends.

A database-backed **cluster coordinator** manages the fleet:

- **Node heartbeats & cluster registry:** Every node records periodic liveness heartbeats against a synchronized database clock. Nodes that miss heartbeat cycles are automatically marked offline.
- **Leader election & singleton leases:** Background tasks that must run exactly once (schema migrations, daily mail delivery, job scheduling sweeps) are fenced behind a lease that only the elected leader holds.
- **Monotonic fencing tokens:** Every write to shared database rows or file-system artifacts is gated by a monotonically increasing token. If a node's lease expires, the coordinator immediately cancels all in-flight work on that node — preventing stale writes from corrupting state.
- **Job quarantine & recovery:** When a crashed node comes back online, its abandoned jobs are swept into a quarantine state so healthy nodes can claim and restart them cleanly.
- **Per-node capacity gating:** Each node advertises its maximum concurrent job capacity. Jobs that exceed the fleet's total capacity are queued rather than overloading individual nodes.

A reference **HAProxy docker-compose** with sticky balancing is included, along with a `GET /healthz` probe endpoint that load balancers can poll for readiness.

```bash
# Verify the cluster health probe
curl -s http://portal-node-1:5000/healthz
# {"status":"Healthy","node":"node-1","leaderToken":42}
```

### SQLite-to-PostgreSQL Migration Engine

**Audience:** Administrators

**Problem:** Existing single-node deployments have years of execution history, user memberships, and report metadata locked in SQLite. Migrating this data manually to PostgreSQL would be error-prone and risky.

**Solution:** The new `etl-sql admin migrate-database` command copies all existing data from SQLite to PostgreSQL with multiple safety nets: automatic type coercion between SQLite's dynamic types and PostgreSQL's strict types, foreign-key ordering bypass during bulk load, identity-sequence resync after insert, and row-count verification per table. The migration is **fail-closed** — any mismatch aborts the entire operation with a detailed error report rather than leaving the target in a partial state.

```bash
# Always dry-run first to preview the migration plan
etl-sql admin migrate-database --from sqlite --to postgres --dry-run

# Execute the migration
etl-sql admin migrate-database --from sqlite --to postgres
```

### Shared Artifact Storage (`IArtifactStorage`)

**Audience:** Administrators

**Problem:** In a multi-node deployment, report templates, uploaded files, and snapshot archives stored on a single node's local disk are invisible to other nodes, causing 404 errors and inconsistent behavior depending on which node serves the request.

**Solution:** A new `IArtifactStorage` abstraction ships with two providers — **Local** (for single-node) and **SMB/UNC** (for clusters). When configured with a shared network path, all nodes read and write artifacts to the same location. `SecurityService` policies validate that file access stays within the configured artifact boundary, preventing path-traversal attacks.

### Job-Scoped State Persistence

**Audience:** Script Authors

**Problem:** Long-running ETL jobs that fail partway through have no way to record how far they got. Re-running from scratch wastes time and risks duplicating data in append-mode targets.

**Solution:** Two new built-in functions — `GET_JOB_STATE(key)` and `SET_JOB_STATE(key, value)` — let scripts checkpoint arbitrary key-value state during execution. State updates are buffered in memory and committed atomically to the database only when the job succeeds, so a failed run never leaves behind a misleading checkpoint. A local `.etlstate` JSON fallback is available for environments without a database-backed state store.

```sql
-- Resume an incremental load from the last successful watermark
SET @watermark = COALESCE(GET_JOB_STATE('last_order_id'), '0');

SELECT * FROM source.dbo.Orders
WHERE OrderId > @watermark
INTO #new_orders;

INSERT INTO warehouse.dbo.Orders SELECT * FROM #new_orders;

SET_JOB_STATE('last_order_id', (SELECT MAX(OrderId) FROM #new_orders));
```

### JSON Schema Contract Checks

**Audience:** Script Authors · Evaluators

**Problem:** Upstream schema changes — a renamed column, a widened data type, a dropped field — silently break ETL pipelines, often not discovered until a downstream report shows incorrect data days later.

**Solution:** The new `EXPECT SCHEMA FROM spec.json` statement validates the live source schema against a JSON specification file at the start of execution. If the source no longer matches the contract, the job fails immediately with a clear diagnostic listing every violation, giving teams time to update their pipelines before bad data propagates.

```sql
-- Validate the source schema before extracting
EXPECT SCHEMA FROM 'contracts/orders_v2.spec.json';

SELECT * FROM source.dbo.Orders INTO #orders;
```

### Certified OIDC Authentication

**Audience:** Administrators

**Problem:** Organizations using identity providers like Azure AD, Okta, or Auth0 had to maintain a separate set of ETL-SQL credentials, creating password sprawl and an additional attack surface.

**Solution:** The Portal now supports federated OIDC authentication with full login, logout, and token-refresh flows. User identity is bound to the `sub` claim, and group memberships are dynamically mapped from OIDC claims to ETL-SQL roles — no manual sync required. All OIDC diagnostics (token exchanges, claim parsing, error responses) are emitted with sensitive fields redacted to prevent credential leakage into logs.

## Improvements

### Language & Engine

- **Pushdown aggregation & staged extracts:** `SELECT INTO #temp` statements now push `GROUP BY`, aggregates, `DISTINCT`, and join predicates down to the source database, reducing the volume of data transferred over the wire.
- **Cross-connection semi-join pushdown:** When a small local temp table is joined to a large remote table, the engine now rewrites the join as a parameterized `IN` filter pushed to the remote database — avoiding full table scans on the remote side.
- **Evaluator allocation reduction:** `Row.TryGetValue` is now allocation-free, and a unified `TryResolveIdentifier` path eliminates redundant dictionary lookups during expression evaluation.

### VS Code Extension & IDE

- Enhanced language-server integration with updated syntax highlighting and diagnostic reporting for new v0.12.0 language features (`GET_JOB_STATE`, `SET_JOB_STATE`, `EXPECT SCHEMA`).

## Performance

- **Pushdown aggregation reduces data transfer** — Queries that aggregate or deduplicate before loading into temp tables now execute the aggregation on the source database rather than pulling raw rows. Workloads with high fan-in (many source rows to few aggregate rows) see the largest benefit.
- **Cross-connection semi-join pushdown** — Small-to-large cross-database joins that previously required a full remote scan are rewritten as parameterized `IN` filters, cutting remote I/O proportionally to the selectivity of the local table.
- **Allocation-free row access** — `Row.TryGetValue` and the unified `TryResolveIdentifier` path eliminate per-row heap allocations in the expression evaluator, reducing GC pressure during large-scale evaluations.
- **PostgreSQL connection pooling** — Multi-node deployments benefit from database-native connection pooling and transaction isolation, replacing the local locking loops used by the SQLite backend and improving throughput under concurrent Portal API requests.

---

## Security

- **Monotonic fencing tokens** prevent split-brain data corruption. When two nodes temporarily believe they are the leader, the fencing token on every shared write ensures that only the node holding the highest token can commit — the stale node's writes are rejected and its in-flight jobs are cancelled.
- **Shared Data Protection key ring** — All nodes in an HA cluster share a common key ring for encrypting cookies, anti-forgery tokens, and session state, ensuring that a request routed to any node can decrypt material originally encrypted by another.
- **OIDC credential redaction** — Token exchange payloads, claim values, and error responses in OIDC authentication flows are redacted in all log and diagnostic output to prevent credential leakage.

## Upgrade Guide

### Single-Node Deployments (SQLite)

Standard upgrade — replace binaries and restart services. No configuration changes required.

### Multi-Node HA Deployments (New)

1. **Stop all ETL-SQL services** on every node.
2. **Configure PostgreSQL** as the database provider in `appsettings.json` on every node:
   ```json
   {
     "Portal": { "Database": { "Provider": "Postgres", "ConnectionString": "..." } },
     "Orchestrator": { "Database": { "Provider": "Postgres", "ConnectionString": "..." } }
   }
   ```
3. **Dry-run the migration** to preview the data-copy plan:
   ```bash
   etl-sql admin migrate-database --from sqlite --to postgres --dry-run
   ```
4. **Execute the migration:**
   ```bash
   etl-sql admin migrate-database --from sqlite --to postgres
   ```
5. **Configure shared artifact storage** — set the `ArtifactStorage:Provider` to `SMB` and provide a UNC path accessible by all nodes.
6. **Configure shared Data Protection key ring** — ensure all nodes point to the same key-ring path or database table.
7. **Ensure identical keys** — JWT signing key, orchestrator encryption key, and dataset encryption key must match across all nodes.
8. **Deploy a load balancer** with session affinity (sticky sessions). A reference HAProxy docker-compose is included in the release assets.
9. **Start services** on each node and verify with `GET /healthz`.
