# Flaky Tests — noted during v0.18.0 development, fix in v0.19.0

Tracking note for flaky tests hit while building v0.18.0. Policy unchanged from
[v0.15.0](v0.15.0-flaky-tests.md) and [v0.17.0](v0.17.0-flaky-tests.md): **don't fight a flaky test
repeatedly** — stabilize the minimum to ship, record it here, and fix the class of problem in a
dedicated pass afterward.

## Observed, not yet stabilized

- **`SubscriptionIntegrationTests.Verify_Subscription_Failure_Scenario`** — failed once in a
  full-suite Portal run (936 passed, this one failed) at **16 s**, then passed in isolation, and
  passed again when run together with the `AdminIdentityScope*` classes added in the same change.

  Checked for a causal link rather than assumed: `PortalWebFactory` gives every instance its own
  GUID-named temp directory and SQLite file, so the new tests cannot pollute its state, and the
  areas do not overlap. The 16-second runtime against a sub-4-second isolated run puts it in the
  same family as the entries below — a wall-clock budget met slowly on a loaded machine, not a
  logic failure. Recorded rather than chased, per the standing convention.

- **`HostedServiceLaneTests.MissingDatasetAtRestKey_WithoutFallback_StopsApplication`** — failed once
  in a full-suite Portal run, then passed in isolation and passed the next full-suite run. Roughly
  one failure in a dozen full-lane runs across this development cycle.

  The test starts a real host with no dataset at-rest key and waits up to **15 seconds** for
  `DatasetAtRestKeyValidationService` to stop the application. It is the same class as the v0.15
  `SchedulerServiceTests` and v0.17 `ProcessJobExecutorChaosTests` failures: a wall-clock budget on
  work that a saturated machine can exceed while behaving correctly. `HostedServiceLaneTests` is the
  one Portal suite that starts the **full** `IHostedService` pipeline, so it is both the slowest to
  reach a decision and the most sensitive to load from the ~600 tests running around it.

  Deliberately left alone for now rather than widening the timeout on a guess. The right fix is the
  same shape as the v0.17 one — make the signal wait on the *event* rather than a duration, by having
  `WaitForStop` observe `IHostApplicationLifetime.ApplicationStopping` with no upper bound and let
  the xunit-level timeout be the backstop. That removes the budget entirely instead of moving it,
  and it applies to all four startup-validator tests in the file at once.

  Not a product defect: the validator stops the application correctly every time; only the observer's
  patience is in question.

- **Browser lane — the whole assembly failed at fixture init.** ~~Reproduces roughly every other
  run.~~ **Root-caused and fixed.**

  The symptom was `InvalidOperationException: The server has not been started or no web application
  was configured`, every test in the assembly reporting a millisecond, roughly every other run when
  the lane was launched again straight after a previous run.

  The cause was a **machine-wide SQLite database**: the security-event outbox defaults to
  `%LocalAppData%/ETL-SQL/Security/security-events.db`, opened by `Program.cs` before the host is
  built. A previous test process still shutting down held it, so the next host failed to start at
  all — which is why the failure was total, instantaneous, and immune to anything done inside the
  test assembly. `PortalWebFactory` now points each factory at its own file via
  `ETLSQL_SECURITY_EVENT_OUTBOX_PATH`. Three consecutive full-lane runs went from alternating
  total failure to identical results.

  Two earlier fixes were made while chasing this and are worth keeping on their own merits, though
  neither resolved it: `PortalBrowserFactory` disposed the Kestrel host without stopping it first
  (`IHost.Dispose()` only signals shutdown, so teardown raced the temp-directory deletion), and each
  browser test class had its own `IClassFixture`, so xunit could build the next class's Portal before
  disposing the previous one. All three browser classes now share one `ICollectionFixture`.

  **The same sharing exists in production**, which is the part worth carrying forward: two Portal or
  Orchestrator processes on one host contend for that file too. Nothing here changes that — the fix
  is scoped to tests — but a deployment running both services on one machine is sharing a SQLite
  database between them.

## Measurement lessons

- **A browser test that counts failed requests from session start measures its own setup.** A test
  creating a user goes through the forced password change, and `MustChangePasswordMiddleware`
  answers **403 to every API call** until it is cleared. Counting from session start attributed all
  of those to the page under test and reported three endpoints as broken that were not
  (`/api/branding`, `/api/auth/providers`, `/api/folders` — the first of which is `[AllowAnonymous]`,
  which should have been the clue).

  Snapshot the count after sign-in completes and measure only the delta. Doing so shrank a
  four-endpoint "finding" to one real defect.
