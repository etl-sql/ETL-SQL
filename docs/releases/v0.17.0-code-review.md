## Findings

### H-1 — FIXED: report authorship survived deprovisioning (privilege persistence)

**Status:** Fixed across `65b2ca2e`, `e512dccd`, and `61d941ab`. Introduced *within* this release
cycle — **no released version is affected.** Found by the release gate, not by review.
**Components:** `FolderPermissionService.GetEffectiveReportPermissionAsync`,
`ReportsController.CreatorCanResolveAsync`, `CatalogController.VisibleReportsQuery`, and the
access-request approve/deny/pending endpoints.

The consumer-discovery work added report creator ownership as an **unconditional short-circuit** in
**five** places, each evaluated before any ACL was consulted. Two were caught by pre-existing tests;
the other three were found by sweeping for the same pattern once the first two were understood:

```csharp
if (report.CreatedBy == userId) return FolderPermission.Manage;   // interactive access
if (report.CreatedBy == creatorId) return true;                   // anonymous share/embed
```

Consequences — both caught by security tests that predate v0.16.0:

1. **Interactive.** A user removed from their LDAP group, then re-authenticated, kept `Manage` on
   every report they had authored. `PortalLdapIntegrationTests` expected `Forbidden`, got `OK`.
2. **Anonymous.** `CreatorCanResolveAsync` exists *solely* to gate anonymous share/embed resolution
   on the grantor's **continuing** access — that is what the `PermissionLost` state means. The
   short-circuit made self-authored links immortal, and the admin anonymous-access inventory kept
   reporting them `Active`, so an operator auditing the inventory saw nothing wrong.
   `AnonymousReportAccessTests` expected `NotFound`, got `OK`.
3. **Catalog visibility.** `VisibleReportsQuery` gained an unconditional `r.CreatedBy == userId ||`
   clause this release (v0.16.0 had only the ACL check), so a deprovisioned author kept seeing their
   reports in search, favourites, and recents while being unable to open them.
4. **Approval authority.** `ApproveAccessRequest`/`DenyAccessRequest` permitted the author outright.
   Deciding a request *grants access to someone else*, so an author who had lost access could still
   hand it out.
5. **Requester disclosure.** The pending-request listing filtered on authorship, leaking requester
   usernames, emails, and stated reasons to someone who could no longer decide them.

Net effect: removing a user from their groups — or from the directory entirely — revoked neither
their authored reports, nor the **unauthenticated** links they had issued for them, nor their
ability to grant others access. For an LDAP/OIDC-backed deployment this is a deprovisioning failure
on the highest-exposure surface.

**Fix.** Authorship now *upgrades* an existing grant to `Manage` rather than substituting for one:

```csharp
if (report.CreatedBy == userId && (folderPerm.HasValue || directPerm.HasValue))
    return FolderPermission.Manage;
```

A creator who retains folder access or a report ACL still gets `Manage`; one with neither gets
nothing. Admin and folder-ownership short-circuits are unchanged. `CreatorCanResolveAsync` drops its
short-circuit entirely, so anonymous-link authority always derives from real access. The catalog
query uses folder ownership instead of authorship, and the access-request endpoints route through a
single `CanDecideAccessRequestAsync` so the listing and the authority cannot drift apart.

`ReportAuthorshipRevocationTests` pins the rule in both directions — an author removed from every
group loses access, visibility, and approval authority; an author retaining a Read-level grant still
has it upgraded to `Manage`. **Each revocation assertion was verified to fail against its own
re-introduced bug**, so they are guards rather than decoration. 551 Portal tests pass.

The equivalent pattern in shipped dataset code (`DatasetPermissionService` ×2,
`ReportDependencyService`) is byte-identical at v0.16.0 and was deliberately left alone — changing
released behavior mid-release with no test demanding it is how the next regression gets made. It is
tracked in `ROADMAP.md` under *Portal — Authorship Is Not Permission*, tests first.

**Process note.** Two pre-existing tests encoded exactly the right specification and caught this.
The value came from the *gate*, not from reading the diff — a reminder that for permission logic,
"reviewed and looks fine" is much weaker evidence than a red test.

### M-1 — WITHDRAWN: "interpolation leaks sensitive variables into ordinary output"

**Status:** Withdrawn — not a defect. No code change shipped.
**Component:** `src/ETL-SQL.Engine/ExpressionEvaluator.cs`

#### What was claimed (from code reading)

`EvaluateInternal` interpolates any string literal containing `${` (line 367-370) and passes no
decryption intent through. `InterpolateStringVariables` then decrypts an `ENC:` value whenever the
variable is marked sensitive (line 1060-1066) — unconditionally.

The direct variable path does not behave this way: `EvaluateVariable` only decrypts when the caller
passed `decryptSensitive: true` (line 1031-1037), and that flag is passed only by trusted secret
sinks — `CreateConnection`/`AlterConnection` options, file-operation passwords, key passphrases.
Everywhere else (the default) a sensitive variable evaluates to its `ENC:...` ciphertext.

`DeclareStatementHandler` (line 50) evaluates a sensitive variable's initial value with
`decryptSensitive: !stmt.IsSensitive` — i.e. **false** for sensitive variables — so
`DECLARE @pw STRING = 'ENC:...' PASSWORD;` genuinely stores ciphertext at rest. This is the pattern
`ConnectionEncryptionRule` actively lints *for*.

Net effect: `SELECT @pw` yields `ENC:...`, but `SELECT 'x${@pw}'` appears to yield plaintext —
into a result set, a table, an exported file, or a log. That undercuts the same masking intent that
`SHOW VARIABLES` enforces (it masks sensitive values to `*******` unless `ShowPassword` is set).

**Caveat on severity.** This behavior is *documented as intended* in the reference page added this
release ("If the variable is declared sensitive (PASSWORD), encrypted values are decrypted
automatically during string interpolation"). So it is a deliberate design decision, not an oversight
— the question is whether the decision is right, given that the legitimate use case (building a
connection string from `${@pw}`) already runs under `decryptSensitive: true` and would keep working
if interpolation honored the flag.

**Exploit precondition:** the actor must be able to author or edit a script that already references
the secret. That is a meaningful bar for a trusted operator, but *not* for the Portal/SaaS
catalog-only authoring profile, where script authors are explicitly semi-trusted and the whole
`SECRET:`/masking design exists to keep secret values away from them.

#### What testing actually showed

A probe against a real evaluator (`USE PASSWORD`, a `PASSWORD` variable holding a genuine
`CryptoUtils.Encrypt` value) produced:

| Expression | Result |
| :--- | :--- |
| `SELECT @pw` | `ENC:AiOq…` — ciphertext, as expected |
| `SELECT 'lit=${@pw}'` | `lit=${@pw}` — **placeholder left intact; not interpolated at all** |
| `DECLARE @x STRING = 'x=${@pw}'` | `x=super-secret-value` — plaintext |
| `DECLARE @x STRING = @pw` | `super-secret-value` — **plaintext, and this predates v0.17.0** |

Both premises of the finding were wrong:

1. **The claimed leak path does not exist.** A string literal in a `SELECT` projection does not
   resolve variables during interpolation at all, so there is no "interpolation yields plaintext
   where a direct reference yields ciphertext" asymmetry to exploit.
2. **The real plaintext path is not new and not interpolation-specific.** `DECLARE` of a
   *non-sensitive* variable evaluates with `decryptSensitive: true` (by
   `decryptSensitive: !stmt.IsSensitive`), so it decrypts a sensitive source. But a plain
   `DECLARE @x STRING = @pw` does exactly the same thing and has always done so — interpolation adds
   no capability. Sensitive-variable masking is therefore **display hygiene for `SHOW VARIABLES`,
   not a containment boundary against someone who can author the script**, and it was never
   documented or built as one.

The proposed 3-line fix (threading `decryptSensitive` into `InterpolateStringVariables`) was
implemented and measured against the same probe: **output was byte-identical to baseline in all four
cases — a complete no-op.** It was reverted rather than shipped, along with the two tests written
against the incorrect expectation. Shipping a no-op change justified by an incorrect threat model
would have added a misleading security narrative to the release.

#### Genuine (non-security) observation carried forward

`${var}` interpolation resolves in `DECLARE` but **not** in a `SELECT` projection literal, while
`docs/reference/statements/expressions-and-operators.md` states it "works across all statement
options, file paths, dynamic connection settings, and expressions." A `SELECT` projection is an
expression, so either the behaviour or the documentation is wrong. Not a security issue and not a
release blocker — logged for v0.18.0.

## Cleared — reviewed, no action

- **`WEBHOOK` connector.** Egress policy (`ConnectorPolicyAuthorizer.EnforceEnterpriseUrl`) is
  enforced in the constructor *and* re-validated on every redirect hop. Auto-redirect is disabled;
  only body-preserving 307/308 are followed, with 301/302/303 rejected explicitly so a POST is never
  silently downgraded to a GET. Redirect cap with loop detection, per-hop timeout, scheme restricted
  to http/https. The URL is treated as a credential and masked to scheme + host in `ToString`,
  `GetConfig`, and error text. The `_context != null` guard on the redirect hop is defensive only —
  the constructor takes a non-null context and validates unconditionally.
- **Quarantine disposition `UPDATE` construction.** Column names pass an identifier allowlist
  (`IsSafeReplayTarget`: letters/digits/`_`/`#`/`@`, no dots) and `__dq_*` evidence columns are
  rejected. Values and row ids go through `ToSqlLiteral`, which doubles single quotes. Verified
  against `Lexer.ReadString`: the dialect treats **only** `''` as an escape and does not honor
  backslash escapes, so quote-doubling is complete here — no injection path. Row ids are length- and
  control-character-bounded; edited columns are capped at 50.
- **Report-level ACLs.** `GetEffectiveReportPermissionAsync` returns the **max** of folder permission
  and report ACL, so a report grant can only widen access, never silently narrow it. Admin and report
  creator short-circuit to `Manage`. The new per-user group-id cache lives on a service registered
  `AddScoped`, so it cannot leak group membership across requests.

## CodeQL triage (first scan of this release's code)

CodeQL runs only on `main`, so v0.17.0's 219 commits — 197 changed C# files and 36 JS/TS files —
were unscanned until the release branch was merged. The scan on `8fee49a5` raised **10 alerts**
(5 High, 4 Medium, plus one High C#). Nine were dismissed as false positives with per-alert
justification recorded in GitHub; one is left open deliberately.

**This is the argument for merging to `main` before tagging.** Tagging off the release branch would
have published v0.17.0 with none of this analysed.

### Dismissed — sanitizer or guard not followed by the analysis

| # | Rule | Why it is not reachable |
| :--- | :--- | :--- |
| 320, 322, 324, 326 | `js/xss`, `js/client-side-unvalidated-url-redirection` | Sink is `img.src = safeUrl(...)`. `safeUrl` returns `#` for any scheme other than `http`/`https`/`mailto`, so `javascript:` cannot reach it. |
| 321, 325 | `js/xss`, `js/…url-redirection` | `a.href` is gated on an explicit `/^https?:\/\//i` allowlist with a `#` fallback. |
| 327 | `js/…url-redirection` | Navigation gated on `/^\/(?![/\\])/` — one leading slash only, rejecting protocol-relative `//host` and `/\host`, so a crafted report name cannot redirect off-site. |
| 328 | `cs/sql-injection` | `PRAGMA table_info()` cannot take a bound parameter in SQLite, so interpolation is unavoidable. The identifier is double-quoted with embedded quotes doubled (`QuoteIdentifier`), making it one quoted literal that cannot terminate early. |
| 329 | `cs/insecure-sql-connection` | `SqlConnectionStringBuilder` here only *parses* an existing string to read `DataSource`; it never opens a connection. |

### Open — alert 323, `js/xss`, accepted for v0.17.0

`report-runtime.js` builds a lineage-tree node with `innerHTML`. Every string field is escaped —
`escHtml(node.name)`, `escHtml(node.status)` — but two values are interpolated raw:

```js
if (node.durationMs    != null) timeStr = `[${node.durationMs}ms]`;
if (node.rowsProcessed != null) rowsStr = `(${node.rowsProcessed} rows)`;
```

The author escaped strings and treated these as numbers. That is an assumption, not an enforcement.

Accepted for this release on two findings of fact:

1. **Not introduced by v0.17.0.** The identical lines exist at `v0.16.0` (canonical file, lines
   3922/3925). The alert is new only because `sync-assets` began copying the runtime to
   `src/ETL-SQL.WorkstationEditor/wwwroot/`, a path CodeQL scans — a *visibility* change, not a
   code change.
2. **Not user-reachable.** Both fields come from engine telemetry
   (`evaluator.Telemetry.RowsProcessed` in `EngineRunner.cs`), which is numeric.

Left **open** rather than dismissed: it is a genuine latent gap, and marking it "false positive"
would be untrue. Hardening is queued as v0.18.0 work in `TODO.md`.
