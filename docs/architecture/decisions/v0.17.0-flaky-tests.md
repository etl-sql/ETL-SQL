# Flaky Tests — noted during v0.17.0 release, fix in v0.18.0

Tracking note for flaky tests hit during the v0.17.0 release. Policy is unchanged from
[v0.15.0](v0.15.0-flaky-tests.md): **don't fight a flaky test repeatedly during a release** —
stabilize the minimum to ship, record it here, and fix the class of problem in a dedicated pass
afterward.

## Stabilized during v0.17.0

- **`ProcessJobExecutorChaosTests.Timeout_KillsChildProcess_AndClearsActiveProcessTracking`** —
  wall-clock budget assertion, same class as the v0.15 `SchedulerServiceTests` fixed-delay failures.

  The test spawned a child that sleeps 10 seconds, configured a 1-second executor timeout, and then
  asserted the whole call completed in **under 8 seconds**. The bound is what proves the timeout
  fired instead of the child running to completion, so it is load-bearing — but it left only ~2
  seconds of headroom below the child's own sleep. During the v0.17.0 standard lane, with the
  machine saturated, process spawn + kill + teardown exceeded that budget and the test failed while
  the timeout logic was working correctly. It passed 3/3 in isolation at ~1s each immediately
  afterward.

  Stabilized by widening the *discriminating gap* rather than loosening the assertion: the child now
  sleeps 120 seconds and the bound is 60 seconds. Any completion well under 120s still conclusively
  proves the timeout fired, while a starved run has an order of magnitude more slack. The assertion
  also gained a failure message naming what it is distinguishing.

- **`ProcessJobExecutorChaosTests.CallerCancellation_KillsChildProcess_AndClearsActiveProcessTracking`**
  — not observed failing, fixed alongside because it is the same shape: a 1-second caller
  cancellation against a 10-second child with the same `< 8` bound. Left alone it would have been
  the next flake.

## Class of problem to fix in v0.18.0

Both cases are *timing assertions sized against a competing duration that is too close to them*. The
v0.15 pass replaced fixed `Task.Delay` sleeps with `WaitUntilAsync` polling; that pattern does not
apply directly here, because these tests are asserting an upper bound on elapsed time rather than
waiting for a condition.

The audit worth doing:

- Find duration assertions where the bound sits close to the duration it is meant to exclude. A
  bound is only safe when the gap between "correct behaviour" and "the thing being ruled out" is
  wide relative to scheduling jitter under load.
- Prefer asserting an observable outcome over elapsed time where one exists — for these tests the
  timeout/cancellation outcome and `tracker.ActiveCount == 0` already carry most of the meaning, and
  the clock is only distinguishing *why* the run ended.
- `scripts/check-flaky-test-delays.mjs` already guards fixed delays; consider extending it to flag
  elapsed-time upper bounds whose margin is under some multiple of the competing duration.

## Investigation result for v0.18.0

- The two `ProcessJobExecutorChaosTests` cases already had the correct wide discriminating gap:
  a 120-second child process and a 60-second assertion bound. They now carry
  `flaky-time-bound-ok` annotations so the CI guard preserves the review decision.
- `CancellationTests.CancelRun_StopsActiveRun_AndEditorStaysReusable` had the same fragile shape in
  a smaller form: the stopwatch included the wait for the editor to enter `IsRunning`, then reused
  that elapsed time to assert cancellation completed promptly. The test now starts a separate
  stopwatch after `CancelRun()` so scheduler delay before the run starts cannot fail the
  cancellation assertion.
- `scripts/check-flaky-test-delays.mjs` now also flags unreviewed elapsed-time upper-bound
  assertions in ordinary test code. Valid upper bounds must either be replaced by observable
  outcomes or annotated with a reason that explains the discriminating gap.
