# v0.17.0 Performance Results — Smoke Scale Certification

**Status:** Decision record. The v0.17.0 release gate ran with `-SkipScale`; the rationale and the
measurements behind that choice are below.

## Summary

The smoke scale-certification **baseline comparison** failed for
`ExternalJoin_50000_equality` (~61% slower elapsed, ~38% lower throughput than the checked-in
baseline). A cross-version measurement shows **v0.17.0 did not cause it**: the released v0.16.0
measures the same. The checked-in baseline has been stale relative to shipped code since at least
v0.16.0.

Certification **correctness** passed throughout: 13/13 scenarios.

## Measurements

All runs: same machine as the baseline (`CHUCKPC`, Intel Core Ultra 9 275HX, 24 logical cores,
32 GB, same NVMe), idle, build servers shut down, clean build, `-Samples 5`.

| Source | ELAPSED_MS | ROWS_PER_SECOND |
| :--- | ---: | ---: |
| Baseline `baseline-smoke.json` (2026-07-05) | 552 ms | 90,579.7 |
| **v0.16.0** (tag, released 2026-07-19) | **878 ms** | **56,947.6** |
| **v0.17.0** (release candidate) | **888 ms** | **56,306.3** |

v0.16.0 → v0.17.0 is **+1.1% elapsed**, i.e. within run-to-run variance. The step change happened at
or before v0.16.0, which shipped.

### Load sensitivity (why the first reading was misleading)

The gate's own run — taken while the machine had been under sustained test load for hours, with
2.5 GB of orphaned MSBuild/Roslyn server processes resident — reported **4 failures and 7 warnings**,
including `SpillCleanupFailure_50000` and `TempTableSpill_50000_SELECT_INTO`. After
`dotnet build-server shutdown` on an idle machine those two passed and the failure set collapsed to
`ExternalJoin` alone. A single-sample run of the same code also read 717 ms where five samples read
888 ms.

Two conclusions follow, and both matter more than the specific numbers:

1. **This benchmark is load-sensitive enough that a busy machine manufactures failures.** A release
   gate that runs after ~40 minutes of test suites is measuring the machine as much as the code.
2. **`n=1` is not a measurement here.** Any decision taken from a single sample — in either
   direction — is unsound.

## Why the baseline was not re-blessed

Blessing was tried before and deliberately reverted:

- `b53b54e0` (2026-07-12) — *Bless smoke cert baseline for accepted external-op regression*
- `e3fa80af` (2026-07-12) — *Revert noise-based cert baseline bless; defer perf re-validation to v0.16.0*

The revert's reasoning stands: blessing bakes an unexplained slowdown into the reference and
permanently destroys the signal. If the 552 ms → 878 ms step is a real regression, no future run can
detect it once the baseline records 878 ms as normal. The comparison also reports
`CONFIG_FINGERPRINT: missing` and `COMMIT_METADATA: missing`, so it cannot verify that the baseline
and the current run share a performance configuration — which is not a state to freeze a new
reference from.

No join-relevant engine configuration changed since the baseline was captured
(`JoinSpillThreshold`, `ExternalHashPartitions`, `OperatorMemoryGrantMB`, `MemoryGovernorPolicy` are
all unchanged in `src/appsettings.json`).

## Decision for v0.17.0

Ship. The gate runs with `-SkipScale`, which omits only the smoke certification and its baseline
comparison; the Standard tier, Docker integration lane, and spill allocation budget still run.

Justification: the metric is unchanged from the version already in users' hands, correctness is
unaffected, the absolute magnitude is ~0.33 s on a 50,000-row micro-benchmark, and the scale phases
are local-only (CI, CodeQL, and the release workflow do not run them).

## Carried forward — and this is the third time

The same action has now been deferred out of **v0.15.0 → v0.16.0 → v0.17.0** and has never been
performed. v0.16.0 shipped without the "clean-machine re-validation + bisect" its own predecessor
committed to. Deferring it again without changing anything would be a fourth repetition, so the
follow-up is written as concrete work rather than an intention:

1. **Bisect `552 ms → 878 ms` between 2026-07-05 and the v0.16.0 tag.** The window is now bounded on
   both sides by measured values, which is the expensive half of the problem already solved.
2. **Decide from the bisect**, not from the gate: fix the regression, or re-baseline *with the
   commit and rationale recorded* so the number is explainable rather than merely current.
3. **Capture `CONFIG_FINGERPRINT` and `COMMIT_METADATA` in every cert run.** Their absence is why
   every one of these comparisons has been arguable.
4. **Make the gate refuse `n=1` for baseline comparisons**, and either run scale certification before
   the long test lanes or require an idle-machine check, so the gate stops generating false failures
   that cost a release cycle to disprove.
