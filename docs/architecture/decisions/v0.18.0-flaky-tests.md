# Flaky Tests — noted during v0.18.0 development, fix in v0.19.0

Tracking note for flaky tests hit while building v0.18.0. Policy unchanged from
[v0.15.0](v0.15.0-flaky-tests.md) and [v0.17.0](v0.17.0-flaky-tests.md): **don't fight a flaky test
repeatedly** — stabilize the minimum to ship, record it here, and fix the class of problem in a
dedicated pass afterward.

## Observed, not yet stabilized

- **`HostedServiceLaneTests.MissingDatasetAtRestKey_WithoutFallback_StopsApplication`** — failed once
  in a full-suite Portal run, then passed in isolation and passed the next full-suite run. Roughly
  one failure in a dozen full-lane runs across this development cycle.

  The test starts a real host with no dataset at-rest key and waits up to **15 seconds** for
  `DatasetAtRestKeyValidationService` to stop the application. It is the same class as the v0.15
  `SchedulerServiceTests` and v0.17 `ProcessJobExecutorChaosTests` failures: a wall-clock budget on
  work that a saturated machine can exceed while behaving correctly. `HostedServiceLaneTests` is the
  one Portal suite that starts the **full** `IHostedService` pipeline, so it is both the slowest to
  reach a decision and the most sensitive to load from the ~600 tests running around it.

  Deliberately left alone for now rather than widening the timeout on a guess. The right fix is the
  same shape as the v0.17 one — make the signal wait on the *event* rather than a duration, by having
  `WaitForStop` observe `IHostApplicationLifetime.ApplicationStopping` with no upper bound and let
  the xunit-level timeout be the backstop. That removes the budget entirely instead of moving it,
  and it applies to all four startup-validator tests in the file at once.

  Not a product defect: the validator stops the application correctly every time; only the observer's
  patience is in question.

- **Browser lane — the whole assembly fails at fixture init** with
  `InvalidOperationException: The server has not been started or no web application was configured`,
  every test reporting a millisecond. Reproduces roughly every other run when `dotnet test` is
  launched again immediately after a previous run of the same lane; the lane passes in full whenever
  it is not chasing a prior run.

  Two contributing defects were found and fixed along the way, both real and both worth keeping:

  - `PortalBrowserFactory.Dispose` disposed the Kestrel host without stopping it first.
    `IHost.Dispose()` signals shutdown and returns, so Kestrel was still unbinding its port and
    still holding the shared SQLite files while the base factory deleted the temp directory
    underneath it. Teardown now stops the host and waits, bounded at 15s.
  - Each browser test class had its own `IClassFixture`, so xunit could build the next class's
    Portal before disposing the previous one — two hosts briefly alive in one process. All three
    classes now share a single `ICollectionFixture`, which also starts Chromium and the Portal once
    for the lane instead of once per class, and moves the seeded admin's forced password change onto
    the fixture so classes no longer fight over one account.

  **Neither fixed the flake**, which is the useful finding: it survives across separate `dotnet test`
  processes, so the contended resource is not in-process. The remaining suspect is machine-level
  state touched during Portal startup — `SecurityEventRuntime.ConfigureLocalOutboxFactory` and
  `EnterprisePolicyRuntime.InitializeFromMachineAsync` both reach into `LocalApplicationData` rather
  than the per-run temp directory, so a SQLite lock held by an exiting process can block the next
  one's startup. That is a plausible product-shaped issue as well as a test one: two Portal processes
  on one host share it too.

  Deliberately not chased further here, per the standing policy. The next pass should point those two
  runtimes at a per-instance path in tests and confirm the flake disappears, rather than adding a
  retry around `CreateClient()` — a retry would hide a genuine startup failure exactly as well as it
  hides this one. Recorded because the symptom is unmistakable (every test in the assembly failing in
  a millisecond with the same message) and will not be mistaken for a product regression.
