# Flaky Tests — noted during v0.18.0 development, fix in v0.19.0

Tracking note for flaky tests hit while building v0.18.0. Policy unchanged from
[v0.15.0](v0.15.0-flaky-tests.md) and [v0.17.0](v0.17.0-flaky-tests.md): **don't fight a flaky test
repeatedly** — stabilize the minimum to ship, record it here, and fix the class of problem in a
dedicated pass afterward.

## Observed, not yet stabilized

- **`HostedServiceLaneTests.MissingDatasetAtRestKey_WithoutFallback_StopsApplication`** — failed once
  in a full-suite Portal run, then passed in isolation and passed the next full-suite run. Roughly
  one failure in a dozen full-lane runs across this development cycle.

  The test starts a real host with no dataset at-rest key and waits up to **15 seconds** for
  `DatasetAtRestKeyValidationService` to stop the application. It is the same class as the v0.15
  `SchedulerServiceTests` and v0.17 `ProcessJobExecutorChaosTests` failures: a wall-clock budget on
  work that a saturated machine can exceed while behaving correctly. `HostedServiceLaneTests` is the
  one Portal suite that starts the **full** `IHostedService` pipeline, so it is both the slowest to
  reach a decision and the most sensitive to load from the ~600 tests running around it.

  Deliberately left alone for now rather than widening the timeout on a guess. The right fix is the
  same shape as the v0.17 one — make the signal wait on the *event* rather than a duration, by having
  `WaitForStop` observe `IHostApplicationLifetime.ApplicationStopping` with no upper bound and let
  the xunit-level timeout be the backstop. That removes the budget entirely instead of moving it,
  and it applies to all four startup-validator tests in the file at once.

  Not a product defect: the validator stops the application correctly every time; only the observer's
  patience is in question.
